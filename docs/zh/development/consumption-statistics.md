# 用量统计与消耗排行榜

项目的「用量统计」提供密钥分组、模型、密钥、用户四个维度；管理区的「消耗排行榜」另有渠道维度，并提供消耗榜、缓存命中率榜。密钥指 AxonHub 签发给调用方的 API Key。界面不读取完整 Key。

这项 fork 功能参考并适配了以下来源，不能理解为所有统计口径完全相同。字段和部分算法移植自 `claude-code-hub` 的 `0c508eaa`。来源是该版本的 `src/repository/leaderboard.ts`、`src/repository/provider-cache-effectiveness.ts`、`src/lib/request-outcome.ts`、`src/lib/cache-effectiveness/{gate,service}.ts` 和 `src/app/v1/_lib/proxy/affinity/fingerprint.ts`。原项目 MIT 许可保存在 [LICENSE.cch](../../../internal/pkg/usageanalytics/LICENSE.cch)。CCH 没有独立密钥榜，本实现将其用户榜语义扩展到 Key。

## 范围与权限

| 入口 | 数据范围 | 权限 |
| --- | --- | --- |
| `/project/usage-stats` | 当前项目，前端显式传入 `X-Project-ID` | 当前项目的 `read_requests` 或系统所有者 |
| `/leaderboard` | 默认全站，可筛选单个项目 | 系统级 `read_leaderboard` 或系统所有者 |

排行榜只有查看权限，不定义管理权限。菜单、路由和后端查询都执行权限检查；项目级同名权限不授予全站访问。项目筛选选项由专用 `consumptionProjects` 查询提供，只有排行榜权限也能使用，不要求额外的项目管理权限。排行榜查询忽略顶部当前项目，不会意外缩小全站范围。权限检查先于查询缓存读取。

项目用量按「密钥分组 → 模型 → 密钥 → 用户」排列，默认选择密钥分组，点击分组名称展开模型明细。具备项目读取权限时包含其他成员的个人 Key 请求；写入权限和跨项目隔离保持独立。

消耗排行榜按「渠道 → 密钥分组 → 模型 → 密钥 → 用户」排列，默认选择渠道。

独立模型维度按最终调用模型名称合并各渠道的请求，无执行模型记录时使用请求模型。统计包含当前记录与归档记录，同名模型合并为一行，支持模型名称搜索。模型行直接展示请求数、成本、Token 数、成功率、平均首字耗时、平均输出速度和整体缓存命中率。模型缓存榜展示缓存触发请求数、命中率、缓存读取／输入 Token、平均首字耗时、平均输出速度及对应请求成本。有效样本缺失时显示「—」。模型名称左对齐，数值居中。

## 日期、排序与展开

两页共用今天、昨天、本周、本月、全部、指定日期。日期由后端按系统时区计算，本周从周一开始。指定日期传 `YYYY-MM-DD` 起止日，结束日包含整天；内部使用开始日零点到结束日次日零点的左闭右开区间，适用夏令时的 23／25 小时自然日。结束日早于开始日时拒绝查询。

数据库时间由 Ent 统一保存为 UTC。自然日边界先按系统时区计算，再转换为 UTC 参与查询；缓存汇总的时钟和窗口也统一为 UTC。这样 SQLite 的文本时间比较不会把午夜请求归到错误日期，或因服务器时区不同漏掉缓存样本。

「全部」表示保留在系统中的全部请求；清理请求或用量会改变可查询的历史。用户、密钥、渠道切换保留时间范围。表头可排序，排序不改变已展开对象；展开明细随对应父行移动。宽表格在表格区域滚动，模型子行使用连续浅灰底；悬停或键盘焦点进入一行时，整行单元格使用统一主题底色，行高不变、不缩放。候选列表、下拉菜单与轻量按钮使用同一悬停色，深色主题和减少动画偏好独立适配。

表格只挂载可视区域及前后少量行，展开的模型也参与可视区域计算，避免密钥数量增加时一次创建全部单元格。行使用实际高度和普通表格流排列，列宽不随滚动改变。前端读取周期与内存缓存见下方「页面读取与浏览器缓存」；后端保留一分钟结果缓存，密钥显示名只读取 ID、名称、用户、项目和分组字段。

名称搜索支持用户显示的完整姓名、姓名片段和邮箱，忽略大小写。密钥、渠道和模型按各自名称搜索。数值按列居中，排序／展开图标及模型数量不改变文字的对齐位置。

## 请求与金额归属

金额显示精度可在「系统设置 → 常规 → 金额显示小数位数」调整。默认「保持现有精度」沿用各页面原来的位数；管理员选择 0–8 位并保存后，消耗排行榜、项目用量统计、密钥分组和 API 密钥的成本／额度展示按该位数四舍五入并补齐尾零。普通项目用户也会读取该展示设置。切回默认可恢复原来的显示规则。

此设置仅影响前端显示，不修改存储金额、接口返回的成本／额度、统计计算、排序、额度输入值或预算判断。例如原金额 `1.23456789` 选择 2 位后显示为 `1.23`，参与计算的仍是原金额。

请求数和金额按已经结束的请求统计，每个请求只计一次，并归属到其最终渠道。渠道成功率和首字另按该渠道实际执行的尝试统计；圆圆失败、MuzeAI 成功时，分别记圆圆失败和 MuzeAI 成功，整体请求仍为成功。用量先按请求、渠道、项目汇总，再关联最终渠道的最后一次执行，避免执行数与用量行相乘。模型按实际执行模型分组，没有实际模型时使用请求模型。

成本直接累加保存的历史 `total_cost`，不按当前价格重算，不影响定价和路由。界面显示已有依据的金额，不附加「部分未计价」、星号或计价覆盖次数；全部缺少费用依据时显示「—」，明确记录为零的费用仍显示零。单次成本只使用费用完整的请求；每百万 Token 成本进一步要求该请求有输入／输出 Token，费用与 Token 来自同一批样本。单条缺少依据不隐藏其他有效样本的均价；没有有效样本才显示「—」。明确记录为零的费用参与计算，无 Token 的按次费用不混入 Token 均价。总 Token 使用 AxonHub 的输入加输出；输入已经包含缓存部分，不能再加一次缓存读取／写入量。

按 CCH 的实体过滤规则，删除的用户、渠道不出现在各自榜单；Key 榜同样排除已删除 Key。用户榜仍可归集该用户已删除 Key 的保留请求记录。删除对象和清理日志与新统计页面无关，排行榜不提供删除或修订历史金额操作。

`total_cost` 是本次请求最终价格、计费档位和实际渠道／Key 倍率共同确定的实际成本，不使用标准成本替代，也不在计算均价时再次乘倍率。例如标准计费小计为 3、最终倍率为 0.25、有效样本为 110 万 Token 时，实际费用为 0.75，每百万 Token 成本约为 0.681818。迟到的有效结算证据与未计价用量记录一起补全，避免预算已扣款而排行榜仍未计价。

## 模型明细

| 榜单 | 模型子行字段 |
| --- | --- |
| 用户／密钥／密钥分组消耗榜 | 模型、请求数、总 Token、整体缓存命中率、成本、每百万 Token 成本 |
| 渠道消耗榜 | 模型、请求数、成本、总 Token、成功率、平均首字耗时、平均输出速度、单次成本、每百万 Token 成本、缓存系数、整体缓存命中率 |
| 用户／密钥／密钥分组缓存榜 | 模型、缓存触发请求数、命中率、缓存读取 Token、总输入 Token；成本列显示「—」 |
| 渠道缓存榜 | 模型、缓存触发请求数、命中率、缓存系数、缓存读取 Token、总输入 Token |

- 整体缓存命中率（消耗榜及用量汇总）：全部缓存读取 Token ÷ 全部输入 Token，包括未命中缓存的请求；分母为零显示「—」。
- 缓存触发请求（缓存榜）：至少有缓存读取或写入 Token 的请求。命中率＝这些请求的缓存读取 Token 总量÷输入 Token 总量，限制在 0–100%。不把每行百分比相加或平均，不把未触发缓存的请求放进分母。
- 单次成本＝完整计价请求的费用÷完整计价请求数；每百万 Token 成本＝完整计价且有 Token 的请求费用×1,000,000÷这些请求的输入与输出 Token。分母为零时返回空值并显示「—」。归档统计沿用相同样本规则；旧归档费用完整性未知时不冒充完整样本。
- 渠道页「今日各模型用量」提供平均首字（ms）、平均输出（tok/s）、成功率及每百万 Token 成本，不附加计价覆盖提示。三项性能指标沿用下述有效样本规则，仅统计已结束请求；没有有效样本时显示「—」。列表金额、浮层成本汇总及各模型成本统一遵循系统设置的显示小数位，未设置时保留原有 6 位显示。
- 明细只在打开浮层时查询，不随整个渠道列表预加载；打开时每 30 秒刷新，关闭停止轮询。浏览器将明细保留 5 分钟、20 秒内复用；服务端最多保存 64 个渠道／自然日的结果，10 秒内复用并合并并发查询。权限每次重新检查，事务内读取不使用共享缓存；跨自然日使用不同缓存键。关闭或快速重开只取消该次等待，不中断其他调用方共享的计算；共享计算最长 30 秒。后端以同一数据库读取快照按渠道、日期及稳定游标分批查询，每批同时读取最终执行和用量，避免重复扫描与重复加载历史价格；历史费用及标准成本口径保持不变。
- 渠道成功率＝本渠道成功尝试数÷本渠道成功与失败尝试数。上游 400、404、429 都算失败；尚未派发的尝试、本地队列／RPM 拒绝和客户端取消不参与分母。重试和切换渠道不会抹掉之前的失败。请求维度保留最终结果及原有 CCH 排除规则，不与渠道尝试混算。无有效结果显示「—」。
- 首字从本次渠道执行开始，计到首段实际文本、思考内容、工具参数、音频内容或拒绝内容；状态帧、空工具标识和推理签名不算首字。每次重试重新计时。首字节独立记录首次读取上游正文的时间，可能早于有效输出。持久化保留实际毫秒值，不应用路由评分的 10 毫秒下限。缺失计时保持空值。
- 输出速度参考 CCH：每次以 `输出 Token × 1000 ÷（执行总耗时毫秒－首字节耗时毫秒）` 计算，再对有效值求算术平均。优先使用账目保存的执行／用量关联；旧记录只在同请求、项目、渠道的用量唯一时匹配最后一次执行。不会把重试的 Token 合计套到一次执行。缺首字节、非流式、图片／音视频、无输出、输出窗口不足 100 毫秒均不参与；窗口小于总耗时的 10% 且速度超过 5000 tok/s 的明显缓冲样本也排除。请求日志、排行榜、分析与健康采样共用公式，内部路由评分独立。
- 有实测内容的失败、取消执行也可贡献首字／速度样本；它们是否参与成功率另行判断。平均首字只除以有效首字样本数，平均速度只除以有效速度样本数，健康采样跨时间段合并也使用这两个独立分母，不用总请求数加权。
- 仪表板日性能及跨日图例也传递并使用这两个独立样本数；某日只有首字而没有可用速度或用量时仍保留首字。真实 0 毫秒参与平均，未知值保持空值并显示「—」。渠道性能按每次执行统计，无健康采样时也不只取请求的最后一次；模型性能继续取每个请求的最终执行。

消耗榜默认按成本降序。用户／密钥／密钥分组缓存榜按命中率、请求数降序；渠道缓存榜先按缓存系数，再按命中率、请求数降序。缺失值置后，平局以实体 ID 或模型名保持稳定顺序。

## 与 CCH 的对齐边界

对照本地 CCH `0c508eaa`：基础公式同为输出 Token ÷（总耗时－首字节等待），不是扣首个有效内容等待，也不是仅计算可见文字。OpenAI的上游completion_tokens及Gemini的候选＋思考Token均未额外扣除推理Token。扣除等待会使同一请求的数值高于旧版全耗时速度，不代表供应商提速或用户少等了时间。

- CCH单条速率只要求窗口大于零，界面另隐藏窗口不足总耗时10%且超过5000tok/s的值；CCH排行榜要求至少100ms，但没有相同的极端值过滤。Axon统一要求流式文本、至少100ms，并过滤该极端缓冲值。
- CCH排行榜按最终供应商的请求账目求有效速率算术平均；Axon渠道按实际执行求平均，有真实用量的失败／取消也可能贡献速度，日志与模型维度取最终执行。两者样本和分母可能不同。CCH公共状态另有仅成功样本及中位数路径，不能与Axon渠道健康均值直接视为一致。
- Axon每次执行观察上游正文首次读取字节，遇流终态固定结束计时；CCH流路径在最终统计收尾时取总耗时，门禁未运行时还可能以首个块补首字节。尾部处理和首字节采集差异可能改变结果。
- Axon使用速度版本3及统计缓存v5，不把缺少依据的旧归档／健康桶混入新口径；CCH榜缓存版本及刷新策略不同。因此不能用两边不同时间窗口或不同样本的均值证明算法数值完全一致。

2026-11-09泉哥实际请求#63964：输出185Token、总耗时8646ms、首字节4734ms、首内容8541ms。旧公式为21.40tok/s，新公式为47.29tok/s，页面取整显示47；若误扣首内容会得到1761.90tok/s，但当前实现未这样计算。另两条样本#63960为8.83→11.13、#63951为16.01→20.63tok/s。此为同一历史事实的公式对照，不是压测或供应商提速证明。

## 缓存系数

只采集支持的对话格式：Anthropic Messages、OpenAI Chat Completions／Responses、Gemini Contents。按 CCH 规范化工具、系统提示与消息，生成摘要和前缀字节数；理论可缓存量为规范化字节数除以 4 向下取整。摘要区分项目、调用方 Key、格式和请求模型，不保存提示词正文。它只标记统计样本，不参与会话复用或路由。

当前只将成功完成且同请求、渠道、项目恰有一条用量记录的最终执行纳入有效样本；多条用量无法唯一对应最终执行，仍计入可观测样本总数，但不累加有效样本、理论量或实际读取量。失败、取消、截断和没有用量行同样排除。费用和 Token 总量继续包含全部已保存用量，不受此门槛影响。按项目、最终渠道、模型、5m／1h TTL 桶汇总。现有调度器每 5 分钟执行一次，预留 15 分钟终态缓冲；首次运行回看 1 小时，后续从最后窗口续接。固定 5 分钟窗口与唯一键、upsert 避免多实例重复累计，空闲时段直接跳到下一条样本。

跨模型、TTL 或时间窗口汇总时，先累加计数和 Token，再重算系数，不能平均已有分数。计算使用整数万分比：

```text
实际比例 = clamp(实际缓存读取量 × 10000 ÷ 理论量, 0, 10000)
样本量修正 = 有效样本 >=100:10000；>=30:6000；>=5:3000；其余:1000
可观测比例 = 有效样本 × 10000 ÷ 全部样本
置信修正 = 可观测比例 × 样本量修正 ÷ 10000
缓存系数 = 实际比例 × 置信修正 ÷ 10000
```

每步除法截断；界面再除以 10000 展示为 0–1。没有窗口样本时显示「—」。通常滞后约 15–20 分钟，超过缓冲时间才结束的请求可能不进入该窗口的有效样本，和 CCH 的展示级统计边界一致。成本及缓存命中率独立更新。

缓存系数用于比较相近请求条件下的实际缓存利用效果，不是账单折扣，也不等同于缓存命中率。例如全部样本都有效、实际读取量为估算可缓存量的一半时，100 条有效样本显示约 0.50；10 条样本还需乘 0.3，显示约 0.15。不能把 0.50 解读为费用打五折。

### 已知限制与后续修正

2026-11-07 核查确认：只存在一条用量行还不能证明供应商报告了输入用量。无上游用量的按次计费仍可能生成零 Token 行，且当前协议转换会丢失“输入字段缺失”和“明确输入为 0”的差别。因此本轮仅修复多用量归属歧义，不能宣称缓存系数已完整修复；已保存窗口不会自动重算，历史区间仍可能包含旧结果。用户已明确将以下完整修正留作后续任务：

1. 在 Chat、Responses、Anthropic、Gemini 解析时区分缺失、null 与明确零值；流式汇总保留输入计数来自哪个有效事件。
2. 将采集证据传入统一用量并按执行持久化，预算恢复和迟到结算也保留证据；旧数据保持未知。不能用 `prompt_tokens > 0` 或是否开启预算代替真实证据。
3. 为统计窗口确定口径版本与可重算范围，避免新旧证据混算；不改已发布迁移行为，也不凭现有零值猜测回填。
4. 定向覆盖缺失／null／零、分事件流、重试多用量、无预算及恢复路径；核对正常费用与 Token 汇总不受影响，并验证升级与重复汇总。

本轮没有新增 schema/data migration，也没有改变计价和预算。

## 查询、存储与升级

后端入口为 `ConsumptionService`，GraphQL 定义见 [consumption.graphql](../../../internal/server/gql/consumption.graphql)。父行和模型明细一次分组查询，浏览器不下载原始日志计算。密钥分组、模型和渠道名称搜索复用浏览器已取得的完整汇总，密钥分组选择也在这份汇总中筛选。密钥、用户仍由后端搜索原始名称及邮箱，前端延迟 300ms 提交。后端结果缓存 1 分钟，缓存版本随速度口径更新；权限检查始终先于缓存读取。

Ent 新增 `cache_effectiveness_windows`，并给 `request_executions` 增加可空的首字节时间、采集标记、缓存摘要、理论量和 TTL 桶。字段及索引由 Ent 生成管理，不手写 schema SQL，不增加 data migration 版本；已对照直接上游 `v1.0.0-beta10-fork.7`／`b205ae8e`，没有同名字段或迁移冲突。原始上游仍独立记录在 `release.config.json`。

`usage_archives.pricing_complete` 保留计价完整性。速度公式升级为 `speed_version=3`；旧版本 0／1／2 缺少重算依据的归档不混入新速度平均。新增 `kind=execution` 保存每次执行的成败、首字与速度统计，在清理请求前同事务幂等写入；原 `request`／`usage` 费用归属保持。已有原始执行可直接按新口径查询，已清理且从未保存的失败尝试不能补造。`channel_probes` 新增 `speed_sample_count`、`first_token_sample_count`，默认 0；旧桶未知分母不用于跨桶性能平均。对照上游 beta12 后由 Ent 自动升级，无新增 data migration，不改已发布迁移。

请求或用量源记录仍保留时，清理任务同时保护 request／execution 归档；用量先清理后不会因统计归档过期而丢失执行速度依据。源记录结束保留后，过期归档可按原策略回收。

旧请求的缺失采样保持 NULL，不回填猜测值，已有耗时与成本不变。SQLite 已验证旧 schema 升级、重复升级、历史字段保留和窗口唯一约束。SQL 使用各方言共有的聚合表达式，upsert 由 Ent 按方言生成；beta12 合并阶段已完成 SQLite／MySQL／PostgreSQL 隔离升级及重复启动检查；beta12-fork.1 已完成双机 PostgreSQL 生产升级的字段、版本和配置编号集合核对。范围与收据见 [Fork 维护台账](../../fork-maintenance.md#github-独立发布与两层上游追溯)，不等同于生产全部统计业务已验收。

## 密钥分组

密钥与分组维度均可筛选指定分组，候选项来自当前统计范围内有用量的分组。无分组与已删除密钥不参与分组榜，同名但不同项目的分组按独立编号统计；全站范围在组名后附项目名称，选择单个项目时保留原组名。历史用量按当前成员关系聚合；分组改名或移组会更新缓存版本，不等待原结果过期。权限沿用各页面原有边界。分组创建、默认筛选和自助查看说明见[API Key 自助用量](../guides/self-usage.md#管理密钥分组)。

## 页面读取与浏览器缓存

管理端普通数据读取最多等待 35 秒，包含响应正文读取；初始化与当前用户检查最多等待 10 秒，失败后可手动重试。写操作、渠道测试与模型流式请求保留独立契约。切换或离开已接入取消信号的页面时停止旧读取，超时不连续自动重试。

排行榜和项目用量的昨天／指定日期每 5 分钟重新读取，其余范围每分钟刷新；新鲜期与刷新周期对齐。今天、昨天、本周、本月的缓存不跨系统时区的午夜保持新鲜，活动页面在午夜重新读取，后台页面跨日返回时也更新；若午夜前发出的查询在跨日后才返回旧范围，成功结果在 1 秒后重读，失败仍按正常间隔重试。完整统计汇总的浏览器内存缓存按用户、视图、项目及实际查询条件隔离，闲置最多保留 30 分钟；需要服务器搜索或按密钥分组过滤的独立结果仍保留 5 分钟，避免每个搜索词都长期占用内存；已有模型列表仍为 5 分钟。名称搜索或分组选择只派生显示结果，不覆盖完整缓存。后台刷新失败显示错误及重试，同时保留已加载的数据和更新时间。历史费用仍定期校正，不将业务数据写入长期离线存储。金额格式与精度保持不变。

PostgreSQL 无搜索、无指定密钥分组的排行聚合一次选取各请求在同项目、同渠道下的最终执行及统计字段。带搜索或指定分组的查询仍使用按请求索引查找，避免小范围筛选扫描整个时间范围的执行。其他方言、归档及小批量明细保持原路径；统计口径和权限不变。

模型表格只渲染可见行及少量缓冲行；排序、开发者分组和全选仍基于完整已加载列表，滚出视区不清空显式选择或展开状态。接口目前仍先取完整模型列表，没有将大列表渲染优化描述为接口分页优化。

### 渠道控件与公共读取性能

渠道列表只在进入、筛选、翻页或明确刷新时读取。状态、健康门控与负载每 5 秒更新；上游信息和今日用量每 30 秒更新；健康色条每 60 秒读取已生成的采样。每类查询独立，按最多 100 个渠道分批，隐藏相关列暂停对应读取，后台标签暂停轮询。单元格按渠道和字段订阅数据，更新不重建整张表，保留选中、滚动和编辑草稿。读取失败保留上次成功值。

请求页在一次 GraphQL 查询中批量复用渠道和权限读取；会话历史保留页外记录，SQLite 同页共用窗口计算，PostgreSQL 使用实测更快的有界索引查询。渠道上游状态改为两次批量读取，健康门控配置只读取一批，特殊排序仅加载当前页的完整对象。

分组下拉框使用 `consumptionGroupOptions`／`usageGroupOptions`，只返回所选日期内有数据的分组，不重复计算排行榜。权限与项目范围沿用主查询。排行榜与用量缓存版本为 v5，同键并发读取合并计算；调用方离开页面只取消自己的等待，共享计算限时 30 秒。
