# 存储清理、部署迁移与长期维护

系统设置的「存储」页负责应用数据的保留和后台清理；宿主机负责迁移文件、WAL、日志和镜像容量。这两层都需要配置。应用删掉请求记录不代表数据库文件立刻变小，也不能替代备份。

本文对应新增维护实现；安装了较旧版本的服务不会自动获得这些功能。先按[发版与部署流程](../development/release.md)升级，在隔离环境验收，再启用生产清理。下面的路径、账号和时间均为通用示例，必须按部署调整。机器地址、实际路径、容量记录、备份位置及凭据只放在 Git 忽略的 `.local/` 或受保护的机器配置目录，不能提交到公共仓库。

## 新正文使用短期缓存

新请求与响应的调试正文不再写入数据库或长期外存。数据库只保存正文状态和短缓存引用；Token、费用与状态独立保存，不受正文过期影响。该设计参考 CCH 的短期调试留存，使用本机 gzip 缓存，不引入 Redis 依赖。

请求列表只取摘要。完整详情和侧栏按当前标签读取请求或响应正文，执行记录在打开对应标签后查询；音频也在进入响应标签后下载，离开时取消未完成下载并释放页面资源。视频预算恢复仅查询和回读必要字段，不因状态更新连带加载旧大正文。

| 数据 | 最长保留 | 单份原始大小 | 压缩文件总上限 | 数量上限 |
| --- | --- | --- | --- | --- |
| 请求／响应／流式分片调试副本 | 5 分钟 | 5 MiB | 256 MiB | 4096 |
| Responses 续聊必要输入／输出 | 2 小时 | 32 MiB | 512 MiB | 2048 |

`store_request_body`、`store_response_body`、`store_chunks` 分别控制请求正文、响应正文和原始流分片的保存。采集原始分片需要单独开启 `store_chunks`，失败或取消请求已经收到的分片也受这个开关控制。三类调试副本共享表中的 256 MiB 与 4096 条上限。开关持续开启时，内容仍按短缓存期限淘汰。下方按天配置的正文清理处理旧正文及数据库中的引用标记。

总容量上限是每实例 768 MiB 的压缩内容，文件系统元数据另计；达到容量或数量限制时提前淘汰最旧副本。每分钟清理过期文件，读取时也检查期限。超过单份限制只放弃调试保存，不截断实际转发内容。相同正文去重且不延长原期限。页面区分未保存、过期、容量回收和超限。

`request_payload.directory` 默认为 `data/request-payloads`，必须为每个实例使用独立目录；目录内容是可丢弃缓存，不纳入数据库备份。现有请求、响应保存开关继续生效：关闭对应开关后不新增该类正文；任一开关关闭时也不新增磁盘续聊副本。已有有界内存续聊缓存仍独立存在，不能保证重启或过期后恢复 `previous_response_id`。启用磁盘续聊时只保存必要输入／输出，按项目与调用方 Key 隔离，容量回收后同样可能失效。

升级不会主动删除旧数据库／外存正文，也不会缩小数据库文件。旧正文仍可按原接口读取、按下表策略清理。音频二进制资源与视频任务文件继续使用原有独立存储，不属于上述 JSON 缓存上限。调用请求仍需要在处理期间读取完整内容；这个改动控制长期存储和列表读取，不能消除超大请求的瞬时内存开销。

## 配置保留范围

进入「系统设置 → 存储」。保留原有载荷存储和视频设置；自动清理可逐类开关、修改天数后保存。

| 对象 | 新初始化默认保留 | 清理后影响 |
| --- | --- | --- |
| 旧请求体、响应体及正文标记 | 7 天 | 不能再查看相应正文；请求体清理也移除请求头 |
| 旧流式响应块及分片标记 | 3 天 | 不能逐帧回放；默认不持久保存分片 |
| 请求与执行明细 | 60 天 | 请求详情不可再查；删除前保存精简统计 |
| 用量明细 | 60 天 | 原始价格明细不可再查；删除前保存精简统计 |
| 缓存效果窗口 | 60 天 | 只保留此范围的窗口统计 |
| 精简统计归档 | 365 天 | 超期统计被删除，长期查询范围缩短 |
| 渠道探测 | 3 天 | 删除超期探测记录 |

**已有部署的显式设置保持原样**，包括原来关闭的自动清理、原有保留天数。新初始化启用上表各类；升级后应在页面确认并保存自己的策略。期限按记录时间计算，不按备份时间计算。

归档仍是按请求/用量记录保存的精简数字行，不是大小固定的月度总表。它保存归属、模型、请求状态、时间、Token 和成本，不保存正文、请求头或完整价格 JSON。排行榜、仪表板费用和自助用量读取仍保留的明细及归档；原始明细页不恢复被删内容。正在进行的请求、未结算预算占用、标记保留的追踪和线程会跳过。被保留明细引用的请求统计标记可能超过 365 天，以防同一请求重新进入实时统计而重复计数。

预算余额、累计账目、未结算及防重复扣款依据不按日志期限删除。生成视频、手工上传文件、备份文件也不属于这些清理类别，需要单独规划存储生命周期。

## 手动清理与进度

1. 点击「手动清理」，勾选对象并为每类设置保留天数；没有勾选的类别不会因这次操作而清理。
2. 核对影响和候选条数。预览最多查询 10,000 个 ID，超出显示 `≥`；正文类只数候选记录，已经清空的正文在执行时跳过。不同类别可能包含同一请求，不能相加为独立请求数。
3. 展开资源占用，查看整个数据表和索引的大小。它包含未到期内容，不是本次可释放量。SQLite 不提供这条低成本逐表查询时，只显示数据库总量；外部文件大小未知，不扫描所有正文或对象来猜测。
4. 发起任务后查看状态、每类扫描数和实际处理数。页面约 1.5 秒查询一次活跃任务；离开或隐藏页面停止相应轮询，服务端继续处理。重新进入可读回最新任务。
5. 暂停会在当前批次结束后生效；恢复沿已提交位置继续。失败显示在页面，处理原因后手动恢复。普通批次超时或数据库繁忙进入等待，约 30 秒后再试。

自动与手动使用同一个数据库任务位置。活跃任务（含暂停）存在时，新的请求返回该任务，不开第二个清理任务；相同提交编号重试可找回最后一次任务。多进程必须使用同一主数据库，才能共享互斥。一个批次的数据修改和进度在同一事务提交；服务重启后等待原执行者的 30 秒租约过期再接管。页面目前保留最新任务，不提供完整历史任务列表。外存删除是可重试的，无法与数据库组成跨系统原子事务；中断后可能再次请求删除已经不存在的文件。

## 优先保障请求服务

默认每批 100 条、批间隔 250 ms、单批最多 3 秒；连续执行预算为 300 秒，之后让出资源再继续。主库连接使用达到配置上限的 60% 时退让。PostgreSQL 每批锁等待最多 250 ms；锁等待超时会回滚当前批次，保留进度并等待后续继续，无需手动重启任务。其他数据库错误仍显示失败，需要检查原因后恢复。可在「手动配置」调整；先应用配置，再保存页面设置，运行中的任务使用启动时的设置。

这些限制降低竞争，不能保证任何负载下都没有延迟。它们也不是应用的 CPU/内存硬限额：单条大正文、外部对象存储和数据库 I/O 仍影响耗时。首次处理历史积压宜从每批 20–50 条、间隔 500–1000 ms 开始，观察请求成功率、P95/P99 延迟、连接等待、磁盘延迟和 WAL 增长，再调整。压力上升时暂停清理，不能停掉请求转发来追赶清理进度。

自动调度来自部署配置 `gc.cron`，默认 `0 2 * * *`，按 **UTC 02:00** 执行，与界面显示时区无关。任务执行器每 2 秒发现可执行任务；不每次都全表扫描。旧配置中的 `gc.vacuum_enabled` / `gc.vacuum_full` 不会使新在线清理路径执行全库压缩。

## 容量预警与优化

页面占用最多每 30 秒采样缓存，打开页面时约每 60 秒刷新。PostgreSQL/MySQL 查询库和表元数据；SQLite 用页数乘页大小。自动磁盘检测针对应用工作目录，可指定已挂载路径。**容器内磁盘不一定是数据库卷或宿主机磁盘**，远程数据库要在其主机监控。

默认 70% 预警、85% 紧急；自动预留为总盘 15% 与 2 GiB 中较大值。可手动改阈值和预留。可用空间小于预留也触发预警，小于预留一半触发紧急。宿主工具同时报告 inode，避免小文件耗尽文件名资源。

| 检查周期 | 必须关注 | 处理 |
| --- | --- | --- |
| 每 5 分钟 | 数据库卷、正文卷、导出卷、inode 和 WAL 异常 | 接入现有监控；异常才通知，恢复后关闭事件 |
| 每日 | 清理状态、实际增长、导出及过期任务退出状态 | 失败当天处理；不能只看 cron 已触发 |
| 每周 | 表/索引占用、死元组、autovacuum、迁移残留和剩余空间 | 调整保留和批量；估算达到阈值还剩几天 |
| 每月及升级前 | 隔离恢复、核心配置、权限和统计核对 | 记录真实恢复耗时与可恢复时间点 |

用最近 7–14 天同一时刻的占用估算增长趋势；剩余可用空间除以日净增长，可估计到预留线的天数。净增长为零时仍需监控峰值。准备新镜像、数据库升级、临时导出和回滚时需要额外空间；不能把 15% 当作足够任何升级的保证。导出按源库体积预检，导入检查实际目标卷的展开空间。

PostgreSQL 保持 autovacuum/analyze 开启；普通删除主要让页可复用。MySQL 的 `OPTIMIZE TABLE`、PostgreSQL `VACUUM FULL` 和 SQLite `VACUUM` 可能锁表或需要额外空间，必须在维护窗口单独评估。不能因文件没立刻缩小反复清理。镜像只按明确白名单移除已确认不用的旧版本，保留当前及回滚镜像；不能定时运行 `docker system prune --volumes`。

## 跨部署迁移：导出、校验、导入

本阶段提供迁移工具，不要求建设异机备份仓库、连续 WAL 归档或完整灾备体系。已有的页面「备份」页签继续保留；长期自动清理与迁移导出相互独立。

| 方式 | 适用目的 | 会带走什么 |
| --- | --- | --- |
| 页面业务 JSON | 按需迁移少量渠道、模型、密钥等业务配置 | 只有勾选且格式支持的内容；不含完整数据库、新统计归档或外部文件 |
| 页面完整迁移 / CLI PostgreSQL 导出 | 把一个部署的库内数据迁到另一个 PostgreSQL 部署 | 用户、权限、配置、渠道、密钥、预算账目、保留明细及精简统计归档等整个业务库内容 |
| 单独复制外部存储 | 同时迁移需要保留的正文、视频、附件 | 文件系统或对象存储中的实际对象；数据库导出只包含相关引用 |

目标是迁移整个现有部署时，优先使用数据库导出。否则只搬页面 JSON，可能看似渠道已恢复，却缺用户、统计归档或外存正文。数据库导出含敏感配置，必须用受控方式传输，不能放 Git、公开下载地址或聊天内容。集群角色、其他数据库、机器环境变量和外存对象不包含在单库导出中。

### 页面完整迁移（推荐）

进入「系统设置 → 备份 → 完整部署迁移」。只有系统所有者可操作，接口不继承所选项目。
需要 PostgreSQL URL 连接，`pg_dump` / `pg_restore` 与所连接服务器的主版本一致。
官方镜像默认携带 PostgreSQL 17 客户端；其他主版本需在自建镜像中选择对应的
`POSTGRES_CLIENT_PACKAGE`。源应用版本和 PostgreSQL 主版本不能高于目标；
切换后仍按正常启动流程执行 schema 和 data migration，不宣称跨方言或任意旧版本兼容。

1. 在源部署点击「生成完整迁移文件」。任务在后台生成一致快照，离页可继续；完成后点击下载，得到单个 `.axon.tar` 文件。浏览器直接下载，服务端不把整个数据库包放入内存。
2. 在尚未接入业务的新目标部署选择文件并「上传并校验」。上传期间要保留页面；服务端检查固定包结构、实际字节数、SHA-256 和版本。文件通过后显示来源版本、大小和时间。
3. 点「核对并导入」，填写一个**尚不存在**的新库名并确认影响。导入使用临时受限登录账号，后台恢复到独立新库；不覆盖当前初始化库。导出/导入同一时间只运行一个；同任务参数重试不会重复恢复。
4. 显示「新库已就绪，等待切换」后，修改目标部署连接中的数据库名并重启。使用源账号重新登录，核对用户、渠道、密钥、账目、归档及外存，再切换业务流量。目标库会清掉源清理/迁移任务、更新登录签名并关闭导入的自动备份；原业务 Key 保留。当前应用连接不会自动切换。

仅导入自己从可信来源导出的包：校验和证明完整性，不证明来源可信，原生备份可以携带数据库代码。
外部正文、视频、对象存储、环境变量和机器配置不在包内。最终迁移应在源停止写入后重新导出；
在线快照之后的新请求不会自动合并。工具不会停止请求服务或修改路由。

导出显示真实已写字节；上传显示已传输百分比；恢复数据、索引、事务期间显示实际阶段和最近更新，
不会把“文件读完”显示成“导入完成”。页面离开后导出/恢复继续；上传中离开会中断传输。
中断或超时导入**不自动重放**，新库保留供检查。移除临时文件不会删除新库；
失败的临时恢复角色由后台重试收尾。发生未知结果时先刷新任务状态，不再提交另一份导入。

以下是通用配置示例，实际路径按部署修改，不能将机器资料提交公共仓库：

```yaml
database_transfer:
  work_dir: data/migration
  max_file_gib: 20
  timeout_seconds: 3600
  retention_hours: 24
  database_disk_path: /mnt/database-volume
  restore_reserve_gib: 2
```

对应环境变量以 `AXONHUB_DATABASE_TRANSFER_` 开头，例如 `AXONHUB_DATABASE_TRANSFER_WORK_DIR`。
`work_dir` 必须可写，且文件系统支持原子替换和硬链接；多副本使用同一共享目录或为管理接口固定实例路由。
锁使用主数据库专用会话，文件不自动复制到其他实例。单次任务超时默认一小时，临时文件默认一天后过期，
每分钟进行受锁保护的恢复/过期检查。新任务会移除上一份已结束任务的临时文件，因此需要保留的下载应先另存。

导出按源库大小预检工作卷空间；导入至少按源库体积两倍与 `restore_reserve_gib` 中较大值预检，
另加存储维护策略的应急预留。`database_disk_path` 默认留空；必须指向真实数据库卷的可访问路径，
不可用时禁用导入，不能用应用容器的可用空间冒充远程数据库余量。
运行中继续检查两个卷余量，达到预留线则中止任务；上传超时/取消会中断网络读取。

原生客户端不启用并行恢复，使用低 CPU 优先级并限制会话工作内存。锁、流式处理及限额降低竞争，
并不保证与生产请求没有 I/O 竞争；大库应选择低峰时段并观察数据库负载。
反向代理还须允许相应上传大小、传输超时和流式请求（避免代理层整包落盘/缓冲）。
这些检查不替代数据库主机监控，也不预留实际磁盘配额。

### 命令行迁移（可选）

下列 CLI 使用独立的 `.dump` / `.json` 格式，不能直接上传到页面；页面接收上述 `.axon.tar` 包。
CLI 与网页任务使用不同锁，**不要同时运行两种迁移入口**。

### 四步迁移

入口：[`scripts/maintenance/maintenance.py`](../../../scripts/maintenance/maintenance.py)。需要 Python 3.10+、`psql`、`pg_dump` 和 `pg_restore`。只实现 **PostgreSQL → PostgreSQL** 的单库迁移，不把 SQLite/MySQL 或跨数据库方言迁移伪装成同一个流程。客户端版本应与源/目标主版本兼容；先在目标隔离库试导入。

**1. 配置源机器并导出。** 复制 `scripts/maintenance/config.example.json` 到本机私有目录；填写实际卷、导出目录、状态目录和数据库名称。目录需预先建立。连接用 libpq 的受保护服务文件或环境配置，不在公共 JSON 或命令行放密码。

```bash
python3 scripts/maintenance/maintenance.py --config /etc/axonhub-maintenance/config.json status
python3 scripts/maintenance/maintenance.py --config /etc/axonhub-maintenance/config.json export
```

`export` 以一致快照在线导出，流式写入唯一临时文件，不把整库读进内存；成功后生成一对 `.dump` / `.json` 文件。清单包括 SHA-256、字节数、源库体积和时间。源库已有数据不被修改。导出期间仍能处理请求，之后产生的新请求不在这次快照里。

**2. 把这对文件复制到目标机器。** 同时转移部署配置以及需要保留的外部正文/视频，保持目录或对象键对应关系。目标机器修改自己的私有配置，不能继续指向源机器数据库卷。目标应用暂不连接这个导入库。

**3. 校验并导入目标新库。** `EXAMPLE` 替换为导出返回的真实清单文件名：

```bash
python3 scripts/maintenance/maintenance.py --config /etc/axonhub-maintenance/config.json verify --receipt /var/backups/axonhub/exports/axonhub-export-EXAMPLE.json
python3 scripts/maintenance/maintenance.py --config /etc/axonhub-maintenance/config.json restore --receipt /var/backups/axonhub/exports/axonhub-export-EXAMPLE.json --database axonhub_import_test
```

`verify` 只证明文件完整性和格式头，不代表已成功导入。`restore` 只创建名称合法且不存在的新数据库，拒绝配置中的在线库和任何已有目标库；不自动删库或覆盖。执行账号须有创建目标库和导入对象的权限，建议使用目标应用的数据库所有者；若由管理员导入，切换前核实应用账号的所有权/访问权限。导入单事务失败后保留隔离目标供检查。

恢复前设置 `postgres.restore_monitor_path` 为真实目标数据库卷；至少预留源库体积的 2 倍加应急空间，索引重建等需要更多时提高 `restore_required_gib`。旧清单没有源库大小时必须显式提供预算，不能用压缩包大小推算。该检查不预留实际磁盘配额，导入期间仍需监控其他写入。

**4. 验证后切换。** 用兼容版本在目标环境核对用户登录、渠道/模型/密钥数量、预算余额、近期与历史统计及外存正文。检查导入的定时配置，避免目标误触发不需要的旧计划；确认后再让目标应用连接新库并迁移流量。源库保留用于回退，不立即删除。

一次在线导出不等于无损、零停机切换。正式迁移时需要约定最后一次导出及流量切换窗口；如果源机在导出后继续写入，尾部数据不会自动合并。若必须持续写入且不能丢尾部记录，需要另行采用数据库复制/增量同步，不能靠重复导入覆盖在线库解决。本工具不会擅自停止请求服务或修改路由。

### 防重复、资源限制和导出保留

同一部署的写入维护共用 `state_directory` 的 OS 文件锁；重复调用明确拒绝，原任务继续。默认操作超时 1 小时，POSIX 超时结束本机进程组。写入操作拒绝 `docker exec` / SSH 类 `exec_prefix`：杀掉宿主客户端不保证远端作业停止，也不继承宿主限额。需要容器执行时，在受限的实际执行环境里运行脚本；原生客户端可以直连数据库。远程目标必须检查实际数据库卷，不能拿客户端磁盘冒充。

`status` 不取独占锁，报告可见卷、inode、库表占用和已配置的 WAL 归档错误。正常退出 0，容量/WAL 异常退出 2，命令失败退出 1。接入现有监控或经过审阅的 systemd `OnFailure` 才会主动通知；当前不要求新通知渠道，不自动发送消息或改变请求服务。

导出文件默认保留 7 天且至少保留最新 2 份，可修改 `export_retention_days` / `export_min_keep`。迁移文件仍在使用时，应放到独立归档目录或调整保留期限。先预览，再删除：

```bash
python3 scripts/maintenance/maintenance.py --config /etc/axonhub-maintenance/config.json expire-exports
python3 scripts/maintenance/maintenance.py --config /etc/axonhub-maintenance/config.json expire-exports --apply
```

只处理配置导出目录中本工具格式、成对且大小匹配的普通文件，不递归或跟随链接。异常退出留下的 `.partial`、缺清单文件不自动删；周检查时确认没有进程继续写入后手动回收。不要把临时文件永远忽略。

提供容量和导出过期的 systemd 示例，但不自动安装。执行账号、路径和权限需审阅；timer 使用宿主机时区。通用 service 采用低 I/O 优先级、20% CPU 配额、256 MiB 软/512 MiB 硬内存限制。限制只作用于所属进程，不约束另一个数据库服务。Windows 测试不代表 Linux systemd 已验收；正式部署应小数据试导出/导入后调整。日志使用已有 journal 配额，Docker 应用日志设置大小与份数上限。

页面业务 JSON 沿用既有默认每日/30 天保留及已保存设置；database 载荷存储不再允许作为自动备份目标，因为它不会实际写出文件。原 JSON 保留清理只在成功备份后执行，失败只写日志；异步触发提示也不等于完成，多次点击不共享新清理任务的持久互斥。小配置迁移可用该入口并核对结果，大库迁移使用上方完整部署迁移或流式 CLI。

## 阈值临近、升级和迁移验收

- 进入 70% 或低于预留：检查增长来源、清理暂停/失败、旧导出和 WAL 异常；清理确认过期的正文、日志和迁移产物，必要时扩容。
- 进入 85% 或预留不足一半：暂停新增导出、导入和升级等额外写入，先扩容或移动导出文件，让请求服务优先。核实保留标记和未结算记录，不强删它们腾空间。
- 接近耗尽：不能删除数据卷、`pg_wal` 或数据库文件。由运维决定扩容/切换，有计划地降低持久化内容；工具不自动改请求路由或停服务。
- 升级前：确认导出在隔离库可导入、镜像和源码版本可追溯、空间满足迁移/回退。逐套部署，不同时改动全部实例。新索引首次创建可能影响大表，需评估维护窗口。
- 明细删除后回退到不认识归档的旧版本会漏历史统计，不能靠只换旧镜像恢复完整查询。迁移须选理解当前 schema 的兼容版本。
- 验收记录包括导出/校验/导入结果、数据核对、真实耗时、未迁移的外部资源、最终切换点和回退方式。提供工具不代表已在生产执行或完成迁移。
