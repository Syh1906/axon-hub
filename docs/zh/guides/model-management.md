# 模型管理指南

本文介绍如何在 AxonHub 中管理模型，以及如何通过“模型关联”决定请求可以走哪些渠道。

## 从目录导入模型卡片

模型新建／编辑右侧「模型卡片」标题旁提供「从目录导入模型卡片」。选择开发者和目录模型，核对能力、模态、上下文与价格摘要后导入。它替换右侧整张卡片：工具调用、视觉、温度、推理支持与默认值、输入／输出模态、价格、上下文／输出上限、知识截止及发布／更新日期。左侧开发者、模型 ID、匹配规则、公开 ID、名称、分组等配置保持不变；保存模型后生效。

目录未提供的卡片项恢复为空或关闭；没有价格的目录模型也能导入，原价格会清空。导入价格包含基础项、缓存项及目录阶梯，不残留旧时段配置。左侧选择目录模型时，价格为空仍自动填充；已有 0 元价、计费项、阶梯或时段配置仍保留。两处共用目录转换，不进行汇率换算。

## 核心概念

在 AxonHub 中：
- **模型配置**：接收某个模型 ID 或一类模型 ID，并定义共同的模型能力与渠道关联
- **渠道**：实际的 AI 服务商连接
- **模型关联**：把“某个模型请求”关联到“哪些渠道和上游模型”
- **开发者规则**：按模型的开发者统一配置可复用的渠道规则，同一开发者下的模型默认继承

## 模型关联在请求流程中的位置

模型关联是三层流水线中的**中间步骤**。完整说明请参阅 [请求处理流程](../getting-started/request-processing.md#核心概念三层模型设置)。

简单来说：**API Key Profile 改模型名 → 模型关联选渠道 → 渠道改模型名 → 发给上游**

## 创建规则模型与公开模型 ID

在现有“添加模型／编辑模型”弹窗中选择匹配方式，再设置关联：

| 匹配方式 | 示例 | 接收的请求模型 ID |
| --- | --- | --- |
| 精确 | `gpt-6-luna` | 仅 `gpt-6-luna` |
| 前缀 | `gpt-` | 以 `gpt-` 开头的 ID |
| 后缀 | `-luna` | 以 `-luna` 结尾的 ID |
| 正则 | `^gpt-.*-luna$` | 如 `gpt-6-luna`、`gpt-6.1-luna` |

前缀、后缀按字面字符串比较。正则匹配整个 ID，与实际选路使用同一个后端匹配器。
填写“测试模型 ID”即可查看匹配、不匹配或表达式错误；测试不保存配置、不请求供应商，也不作为保存的前置步骤。
默认点击“创建”只保存模型并返回列表。需要继续配置关联时，可从旁边的“创建方式”菜单选择“创建并关联”，直接进入关联弹窗。配置完成后启用模型。

启用的精确配置优先；没有精确配置时，按规则优先级从小到大选取首个匹配项，同级按配置 ID 从小到大。
禁用或归档的配置不参与匹配。选中配置后若无可用关联，请求失败，不再尝试低优先级规则。

“对外提供的模型 ID”单独决定客户端能发现哪些明确的名称：

- 可填零个、一个或多个 ID；每个 ID 必须符合该配置的匹配规则。
- 留空表示不出现在模型列表和模型详情中，仍可通过符合规则的请求名调用。
- OpenAI、Anthropic、Gemini 模型列表共用这组 ID，不返回正则表达式，也不枚举所有可能匹配的名称。
- 密钥别名只有映射到已公开的 ID 才会出现在列表中；允许模型范围按客户端原始请求名检查，渠道范围仍继续生效。
- 多个 ID 共用此配置的模型卡片能力；能力不同的模型应拆为不同配置。

升级前已有精确模型默认继续公开原 ID；清空公开 ID 并保存后才隐藏。规则重叠时，列表与实际请求使用同一个胜出配置，
低优先级配置不能替隐藏的胜出配置公开名称。

## 模型关联是什么

模型关联的作用，是决定一个模型请求可以落到哪些渠道上。

它本质上回答两个问题：
- 哪些渠道可以参与处理
- 这些渠道上的哪个模型可以作为候选

## 开发者规则继承

内置开发者标识忽略大小写：手输 `OpenAI`、`OPENAI` 或选择目录中的 OpenAI 都保存为 `openai`。已有大小写不同的记录按同一开发者分组、继承规则；自定义开发者名称保留原样。

如果同一开发者的多个模型应该使用相同的渠道规则，可以在模型列表的开发者分组上配置**开发者规则**。开发者规则只选择渠道或渠道标签，不固定具体上游模型；实际路由时，每个模型会自动使用自己的模型 ID 去这些渠道中查找对应模型。

规则模型继承开发者规则时，使用本次请求在 API Key 映射后的具体 ID 查找，不使用规则表达式查找。

默认情况下，模型会继承同开发者的开发者规则，并与模型自己配置的规则合并：

- `priority` 数值越小越先执行。
- 同一 `priority` 下，模型自己的规则优先于继承的开发者规则。
- 模型规则弹窗中的“不继承开发者配置”开启后，该模型只使用自己的规则，不再继承开发者规则。

## 常见的模型关联方式

### 1. 指定渠道的指定模型

把一个模型明确指向某个渠道里的某个上游模型。

### 2. 指定渠道的正则匹配

在某个指定渠道中匹配一批模型。

### 3. 所有渠道的指定模型

让同一个模型可以在所有支持它的渠道中使用。

### 4. 所有渠道的正则匹配

在所有可用渠道中按规则匹配一批模型。

### 5. 按标签选择渠道

只在带特定标签的渠道中查找模型，常用于区分生产、测试或供应商分组。

### 6. 渠道内沿用请求模型

选定渠道后，将本次请求在 API Key 映射后的模型 ID 原样发送给该渠道，不要求提前把每个 ID 加入渠道模型目录。
这项关联可以与固定上游模型关联一起使用。例如同一个 `gpt-6.1-luna` 请求：渠道 A 沿用原名，渠道 B 固定为 `gpt-5.6-luna`。
渠道权限、状态、协议能力和关联条件仍参与筛选。关联弹窗的测试 ID 用于预览此次请求对应的渠道与模型，不发送上游请求。

## 优先级

`priority` 值越小，优先级越高。

通常会把更稳定、更希望优先使用的渠道设置为更小的值。

API Key 生效配置可覆盖同一批已允许渠道的优先级，详见 [密钥渠道优先级](api-key-profiles.md#渠道优先级与模板)。

## 常见使用方式

- 想固定走某个渠道：用指定渠道的指定模型
- 想让一个模型在多个渠道里都可用：用所有渠道的指定模型
- 想匹配一批模型：用正则匹配
- 想按环境或供应商分组：给渠道打标签，再按标签选择渠道

## 系统设置

正式请求在 API Key 映射后，必须解析到已注册且启用的模型，再按开发者与模型的有效关联选择渠道。
不存在、禁用、归档或无有效关联的模型不能回退直连渠道。公开模型接口只返回启用的注册目标及有效别名。
渠道连通性测试保留为受权限保护的管理操作。

| 设置项 | 说明 |
|--------|------|
| 列表中隐藏不可路由模型 | 启用后，公开模型列表会隐藏当前 API Key 结构上选不到可用渠道的已配置模型。直接请求这些模型仍返回 422，管理端模型表不变。 |

启用「列表中隐藏不可路由模型」可进一步隐藏当前 API Key 没有结构上可用关联的注册模型；
请求级条件仍可能拒绝列表中的模型。原「查询所有渠道模型」「回退到渠道」及渠道模型黑名单设置已删除，
旧存储值不会恢复绕过行为。

## 常见问题

### Q: 为什么请求提示“模型未找到”？

首先确认请求名（含 API Key 映射后的目标）已注册、启用且未归档，再检查：
1. 模型关联是否配置正确
2. 渠道是否已启用
3. 渠道是否支持关联中指定的模型
4. 是否被其他限制条件过滤掉

如果该模型应该继承开发者规则，还需要确认模型没有开启“不继承开发者配置”。

### Q: 如何验证关联是否生效？

1. 发送测试请求
2. 在控制台查看 Trace
3. 确认请求实际走了哪个渠道

### Q: 同一个（渠道，模型）组合会重复吗？

不会，系统会自动去重。

## 最佳实践

1. **模型名保持稳定**：优先使用统一、可长期维护的抽象模型名
2. **优先级保持简单**：先让主路径明确，再补备用路径
3. **使用标签**：给渠道打标签，方便按环境或供应商分组
4. **先测试再启用**：配置后在控制台验证请求路由是否符合预期

## 批量关联

列表的模型 ID 旁显示已保存的“精确／前缀／后缀／正则”类型，不通过表达式形状猜测。批量新增的优先级与原关联编辑统一为 0–10 的整数；同渠道多个模型在预览中合并展示，不重复生成渠道条目。

在模型列表勾选多个模型后，点击“批量关联”，选择多个渠道或标签。精确模型默认沿用自身模型 ID，其他匹配规则或改名场景需填写实际转发模型。预览显示待新增及重复规则数量；未匹配项不参与保存。保存逐个执行，成功与错误分别展示，可重试失败项；成功项不会重复提交。每次保存前回读模型，再追加规则并保留其他设置。批次不是跨模型事务。

单模型的关联弹窗提供“批量添加”：可搜索渠道、标签或模型，选择当前筛选结果或同名模型，同时添加多个渠道的多个模型。已有的启用、无条件同目标规则自动跳过；停用或带条件的规则保留，允许另添无条件规则。添加先进入当前编辑草稿，回到原弹窗点击“保存”后生效；取消批量选择保留原有草稿。原界面的 10 条规则限制已移除，长列表在弹窗内部滚动。
