# 自适应负载均衡指南

AxonHub 提供智能的自适应负载均衡系统，能够根据多个维度自动选择最优的 AI 渠道，确保高可用性和最佳性能。

## 🎯 核心特性

### 智能渠道选择
- **优先级分组** - 候选渠道首先按有效渠道优先级分组（数值越小，优先级越高）
- **会话一致性** - 同一对话的请求优先路由到之前成功的渠道
- **健康状态感知** - 自动避开错误率高的渠道
- **公平分配** - 同优先级、同权重时使用历史请求数分配请求；不同权重按从大到小选择
- **延迟感知** - 使用更贴近体验的分流指标：流式请求优先较低首 token 延迟和较高输出吞吐，非流式请求优先较低端到端延迟
- **速率限制感知** - 结合 RPM、TPM、并发占用和 429 `Retry-After` 冷却时间进行排序；未显式配置 `MaxConcurrent` 时，会回退到默认连接跟踪器容量做饱和保护

### 多策略评分系统
负载均衡遵循分层处理流程：首先按**有效优先级**分组（密钥覆盖、标签默认、模型关联依次取值）。组内保留硬限流、配额耗尽及失败退避，再按**权重从大到小**排序；仅同权重使用策略评分。已有会话复用规则不变。以下评分用于同权重候选，不代表可以跨权重分流。

| 层级 | 策略 | 评分范围 | 说明 |
|------|------|----------|------|
| **1** | **关联优先级** | 0-N (越小越优) | 模型关联中定义的硬分组 |
| **2** | **会话感知** | 0-1000 分 | 同一会话优先，确保对话连续性 |
| **3** | **错误感知** | 0-200 分 | 基于成功率和错误历史 |
| **4** | **加权轮询** | 10-150 分 | 同权重候选间按历史负载分配 |
| **5** | **延迟感知** | 0-80 分 | 流式请求看 FTTL + TPS，非流式请求看总时延 |
| **6** | **速率限制感知** | -10000-100 分 | 结合 RPM/TPM/并发占用与 429 冷却时间 |

## 🚀 快速开始

### 1. 配置多个渠道
在管理界面中添加多个相同模型的渠道：

```yaml
# 渠道 A - 主力渠道
name: "openai-primary"
type: "openai"
weight: 100  # 高优先级
base_url: "https://api.openai.com/v1"

# 渠道 B - 备用渠道  
name: "openai-backup"
type: "openai"
weight: 50   # 中等优先级
base_url: "https://api.openai.com/v1"

# 渠道 C - 第三方渠道
name: "openai-third-party"
type: "openai"
weight: 30   # 低优先级
base_url: "https://api.example.com/v1"
```

### 2. 启用负载均衡
负载均衡自动启用，无需额外配置。系统会：

- 自动检测渠道健康状态
- 根据策略评分排序渠道
- 智能选择最优渠道
- 失败时自动切换到下一个渠道

### 3. 发送请求
使用标准的 OpenAI API 格式：

```python
from openai import OpenAI

client = OpenAI(
    api_key="your-axonhub-api-key",
    base_url="http://localhost:8090/v1"
)

# 系统会自动选择最优渠道
response = client.chat.completions.create(
    model="gpt-4",
    messages=[{"role": "user", "content": "Hello!"}]
)
```

## 失败后如何切换与反馈

启用渠道的备用地址后，连接失败、响应超时和 5xx（包括 524）可以在原有重试额度内切换到下一个启用地址；原始 HTTP 错误和协议转换后的错误使用相同判断。切换地址保持本次模型、请求正文和账号 Key，地址耗尽后才交回已有渠道切换流程。400、401、403、429 不因地址故障规则切地址；429 也不会重复尝试同渠道或其他映射模型。

HTTP 413，以及明确包含 `image relay inline images exceed the configured` 和 `request limit` 的 400，视为上游容量拒绝：即使配置了可重试 400，也跳过同渠道的重复请求和换模型尝试，只使用已允许的跨渠道候选。完整历史续聊可使用允许的备用渠道，仍依赖上游响应 ID 时保持来源约束；没有可用候选时返回错误，不删除历史或压缩图片来强行通过。其他 400 不按容量问题处理。上游图片中转大小与客户端整份 JSON 大小并不等价。

错误诊断在上游未提供 `code` 时补充 `upstream_request_too_large`（容量拒绝）、`upstream_timeout`（504/524）、`upstream_first_event_timeout`（流式首个事件超时）或 `upstream_response_timeout`（非流式响应超时）。已有上游错误字段保持不变。整个请求确实耗尽网关期限、且在开始交付响应前由 `Process` 返回错误时，客户端收到 HTTP 504 和 `request_deadline_exceeded`；客户端取消不归为上游超时。已经交付的流式响应不能再改写 HTTP 状态，仍沿用原有流结束处理，本轮未统一其超时错误码。网关产生的 504 不作为上游实际 HTTP 状态写入执行记录。错误展示仍受既有错误隐藏策略控制。

这些处理不增加重试预算、不延长或缩短现有超时、不缓存整个输出等待重试，也不重放已交付的流式内容。备用路径同样不可用或上游持续拒绝容量时仍会失败。

## 📊 负载均衡策略详解

### 模型关联优先级 (Model Association Priority)
- **目的**: 高层级的流量控制和硬分组。
- **机制**: 候选渠道按有效优先级排序：密钥覆盖优先，其次是命中标签的默认值，最后是模型关联的 `priority`。
- **规则**: 数值越小，优先级越高。系统会耗尽优先级为 `N` 的所有候选渠道后，才会考虑优先级为 `N+1` 的渠道。
- **应用场景**: 主备渠道分离、A/B 测试（设置相同的优先级和权重）。

### 会话感知策略 (TraceAware)
- **目的**: 保持多轮对话的渠道一致性
- **机制**: 如果请求包含 trace ID，优先使用之前成功的渠道
- **优势**: 避免渠道切换导致的初始化延迟
- **评分**: 匹配渠道获得 1000 分，否则 0 分

### Responses 加密续聊

请求携带加密历史时，网关按实际响应 ID 或密文内容的 SHA-256 指纹查询生成来源，范围限定在同一项目和调用方 API Key 内。来源记录用于优先复用，不根据 trace/thread 最后一次成功调用推断，因此辅助调用和同模型分支不会抢占当前历史的优先来源。

**完整历史允许切换供应商。** 客户端已经带齐历史，或网关已完整展开 `previous_response_id` 时，优先尝试仍有效且允许会话复用的原渠道；原渠道停用、删除、退出当前模型／权限候选、处于健康门控禁用状态或冷却中时，使用当前允许的 Responses 备用渠道。原凭据或地址失效时，允许使用当前有效配置。切换保留历史内容，不删除密文，也不改成无法承载它的 Chat Completions 接口。是否接受该密文由实际上游决定，网关不承诺任意供应商互通。

切换后下一轮优先采用本轮实际历史的最新来源：有原始响应 ID 时先查其记录，否则查实际输入中最后一项加密内容。从 A 切到 B 后，历史同时包含 A、B 的内容不会因来源混合被本地拒绝。原地址仍有效时优先尝试它；地址故障转移开启后，其余地址按配置优先级尝试，包括排在原地址前面的备用地址。选路、健康门控、调用权限、预算及重试次数限制仍然生效。

**仍依赖原上游保存的响应 ID 时保留严格约束。** 本地未能完整恢复历史、请求仍携带 `previous_response_id` 时，已知来源的渠道、凭据、地址和账号身份必须一致，不能把其他供应商不认识的编号当作完整历史发送。来源冲突或已知来源不可用时返回相应 `409 continuation_error`，包括 `continuation_origin_conflict`、`continuation_channel_disabled`、`continuation_channel_missing`、`continuation_candidate_unavailable`、`continuation_upstream_changed` 和 `continuation_credential_unavailable`。真实历史恢复错误按原规则处理，不因来源偏好可选而被忽略。未知导入 ID 沿用原有选择规则，不补造来源证据。

独立的 `responses_origins` 表在输出生成时登记渠道、凭据不可逆引用、上游地址及账号摘要，不额外保存密文或凭据正文。完整加密输出项、压缩结果、中断快照、`response.done` 和省略可选 `status` 的成功响应均尝试登记；回显的旧输入不重新认领。来源查询或登记失败会记录诊断；完整历史仍可正常交付、保存和重新选路，不因可选来源记录失败再次生成。来源记录独立于调试正文和会话缓存过期，当前不自动到期；它不能代替已丢失的历史正文。

升级前的记录仅接受精确响应 ID 对应的成功执行作为来源证据，不按时间补造密文归属。旧凭据可以通过唯一匹配的脱敏末尾信息恢复；严格 ID 依赖遇到歧义时返回 `continuation_credential_ambiguous`。没有凭据信息时，首次尝试采用渠道现有 Key 选择，同一尝试的重试保留实际选中的 Key。`.syh.15` 已新增来源表及请求失败字段；本次切换策略不新增迁移，也不回填旧密文。

只有尚未交付有效输出、发送结果允许安全重放且预算未耗尽时才自动重试。当前来源尝试不通过轮换映射模型掩盖密文错误；有效备用渠道是否可以尝试仍按既有错误重试规则判断，不修改或丢弃历史。有效输出已经交付或执行结果不确定时不自动重放，未完成工具参数仍保持未完成。恢复和选路前登记请求，失败原因进入请求日志；未调用上游时不创建虚假的执行记录。

在 Responses 流式格式转换中，工具参数增量逐段传递。上游明确将单个工具标记为 `completed` 时，网关补齐尚未下发的输入后缀并及时传递完成标记；之后其他工具失败，不会撤销已完成工具的状态。多个工具交错生成时，新工具开始不会使旧工具提前完成。缺少单个工具完成信号时，补发的完成标记等到本轮生成成功结束，因此这类请求中等待完成标记的客户端可能更晚执行工具。已经传递的异常结束事件不会再追加另一条失败事件；不论是否包含用量信息，均保留失败、未完成或取消的原有结果。

### 错误感知策略 (ErrorAware)
- **目的**: 避开不健康的渠道
- **基准分**: 健康渠道基准分为 200 分
- **评分因素**:
  - 连续失败：每次 -30 分，并在冷却窗口内随时间衰减
  - 最近失败（5 分钟内）：最多 -40 分，并随时间衰减
- **恢复**: 失败渠道会随时间自动恢复优先级，因为时间衰减惩罚会逐渐减少。

### 加权轮询策略 (Weight Round Robin)
- **目的**: 同权重候选间按历史负载分配。
- **算法**: 根据渠道权重对历史请求数进行归一化处理。该评分只在同权重候选间比较；不同权重不再按比例分流。
- **评分**: `150 * exp(-归一化请求数 / 150)`
- **范围**: 10-150 分

### 延迟感知策略 (LatencyAware)
- **目的**: 使用更符合用户体感的延迟指标优先选择更快的渠道
- **机制**:
  - **流式请求**: 使用首 token 延迟 FTTL/TTFT 的 EWMA 和输出吞吐 TPS 的 EWMA
  - **非流式请求**: 使用端到端总时延的 EWMA
- **评分**:
  - **流式请求**: `80 * (0.7 * 首 token 分量 + 0.3 * 吞吐分量)`
  - **非流式请求**: `80 * (1 - latency_ewma / 3000)`，结果限制在 `0-80`
- **中性分**: 没有延迟数据时返回 40 分

### 速率限制感知策略 (RateLimitAware)
- **目的**: 尊重上游速率限制并避免 429 或通道饱和
- **机制**: 结合每渠道的 RPM、TPM、并发请求数和 429 `Retry-After` 冷却时间进行打分
- **评分**:
  - 未触发任何限制时最高 100 分
  - 随使用率接近上限按 `100 * (1 - max_usage_ratio)` 线性降分
  - 任一限制耗尽时返回 `-10000`，作为最后兜底候选
- **并发回退**: 如果未显式配置 `MaxConcurrent`，但默认连接跟踪器提供了每渠道容量，系统仍会按当前在途请求数进行降分，并在完全饱和时将该渠道降为兜底候选

### 健康门控策略 (health-gated)
- **目的**: 让持续失败的「渠道 × 上游模型」退出候选，偶发失败只影响当次请求，并在管理端直接看到哪个组合坏了。
- **选择方式**: 在系统重试策略、API Key Profile 或模型设置中把负载均衡策略设为「健康门控」。其余四种策略行为不变。
- **排序**: 新会话或归属过期后，先按模型关联优先级分组（小值优先）；组内先避开硬限流/不可用候选，再按渠道权重从大到小选择。仅同权重候选用历史负载、延迟及配额评分排序。因此同关联优先级、都可用时，新建权重 15 的渠道优先于权重 10 的渠道，不因缺少历史延迟样本而落后。
- **熔断粒度**: 按渠道与经模型映射后发往上游的实际模型计算；一个模型熔断不影响同渠道其他模型。
- **状态**:
  - **健康 / 不稳**: 正常参与候选；最近 W 分钟内有失败或流式首 token 后断流时显示为不稳，不降权。
  - **熔断**: 连续 N 次计数失败后熔断，本次选路跳过（含会话粘性渠道，但不清除粘性记录）。
  - **试探**: 熔断到期后只放行没有粘性渠道的新会话，同一组合同时只放一个请求；连续 M 次成功后恢复，失败则熔断时长翻倍（有上限）。
- **计数口径**: 5xx、网络错误、超时、空响应、首 token 前断流、401/403 计为失败；429、400/404/422 等请求问题、客户端取消和本地限流排队不计入。
- **全部熔断时**: 选最先到期的组合试一次；仍为计数失败则返回通用 503（不暴露渠道名），请求本身的错误（如 400）原样返回。
- **默认值**: N=5，首次熔断 5 分钟，上限 60 分钟，M=2，W=5 分钟，K=2；渠道可单独覆盖阈值 N，设为 0 表示该渠道关闭熔断。
- **会话归属**（会话粘性为「优先最近选中渠道」时）：会话只在请求成功后建立归属，有 thread 时以 thread 为准。有效保护窗口内保留原归属，避免单次波动造成来回切换；归属熔断或连续 K 次由备用渠道完成时迁移。保护窗口默认 5 分钟，最终发往 Anthropic 的请求声明了合法 1 小时缓存断点时为 1 小时；这是按请求声明的保护窗口，不是上游缓存命中检测。只有归属渠道自身成功或迁移成功才刷新窗口，临时转移不替原渠道续期。窗口结束后按当前配置重新选路，旧粘性记录不能复活过期归属；窗口有效期间不会仅因新增渠道而强制迁移。
- **管理端**: 渠道列表显示熔断/不稳模型数并可「只看异常」；健康详情中可查看每个模型的状态、最近错误与剩余时间，并手动重置。请求详情的「路由决策」显示本次的会话归属、被跳过的组合、是否临时转移、是否最后一试，以及会话是否迁移及原因。
- **通知**: Webhook 可订阅 `channel.health_gate_opened`（首次熔断）与 `channel.health_gate_recovered`（试探恢复）；熔断期间试探失败不重复通知。
- **取消与收尾**: 配置读取和渠道观察锁等待遵守请求 deadline，管理端健康查询也不例外。取消不会应用回退配置或计为上游健康失败。尝试结果登记与会话/路由记录登记各有独立 10 秒收尾预算，会话锁等待也受该预算约束；结果登记超时只释放自身探测占位，不误判恢复。
- **限制**: 状态只保存在进程内存中，重启清零，不在多实例间共享。
- **归属存储**: 配置两级缓存时，健康门控会话归属直接以 Redis 为准，避免旧本地缓存延迟回填覆盖新归属；未配置 Redis 时使用内存。升级后的旧归属会重新选路一次。

## 📈 监控和故障排查

### 关键指标
- **渠道切换频率** - 正常情况下应该较低
- **错误率分布** - 某个渠道错误率过高可能需要检查配置
- **响应时间** - 负载均衡应该优化整体响应时间

### 常见问题

**Q: 为什么请求总是路由到同一个渠道？**
A: 检查是否启用了会话一致性。同一 trace ID 的请求会优先使用相同渠道。

**Q: 渠道不切换怎么办？**
A: 查看错误感知策略的评分。渠道可能仍然健康，或者需要时间恢复。

**Q: 如何验证负载均衡是否工作？**
A: 启用调试模式，查看日志中的渠道评分和排序。

## 🎛️ 最佳实践

### 1. 渠道配置
- 设置不同的权重值体现优先级
- 配置多个不同提供商的渠道提高可用性
- 定期检查渠道健康状态
