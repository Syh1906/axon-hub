## 1. 推荐方案与范围

在现有模型价格和请求费用流程中增加普通、Fast、Ultrafast 三档识别。先确定本次采用哪个计费档位，再选择对应倍率，最后应用已有渠道成本倍率。模式识别、价格计算、预算扣减和费用展示共用同一结果。

用户已明确的行为：上游能够可靠返回实际档位时使用该结果；上游不提供有效标识时按客户端请求计费；倍率支持官方默认与灵活调整。本方案进一步提供渠道级“按客户端请求”选项，覆盖 Codex 登录中转返回值不可靠的已知情况。

计费部分覆盖 OpenAI Chat Completions、Responses，以及项目的 Codex 渠道，包含普通 JSON、SSE 流式和现有 WebSocket 接入。它不改变客户端选择模式、渠道路由或中转端的模式开关；选择某个计费档位不代表网关已经替用户启用了该模式。另将已确认的 Responses 续聊历史恢复缺陷纳入同一轮修复，复用已有不可恢复错误和停止重试规则，详见第 11 节。

前端沿用三个位置：模型页的标准价格编辑、渠道的“模型价格”弹窗、请求列表的成本金额悬浮。模型负责提供标准配置；渠道应用后可单独调整；成本列说明这一次采用的模式、上下文价格与金额。费用和模式不放到“成功”状态旁，不新增响应抽屉费用卡。实施以最终确认的预览为依据。

同时补齐 CCH 风格的 `1M` 长上下文计费标记：只有这次确实采用了长上下文定价规则才显示。Fast / Ultrafast 与长上下文是两个独立维度，允许同时命中；继续使用已有全量阶梯价格，不再额外硬乘一次“长上下文倍率”。

本轮统一需求如下；历史恢复修复与计费调整一并进入实施和验收范围，不仅作为背景问题记录。

| 需求 | 本轮交付行为 | 详细位置 |
| --- | --- | --- |
| 模式计费与上游核验 | Standard / Fast / Ultrafast；有效返回优先、缺失按客户端；可按渠道指定客户端依据 | 第 2–3 节 |
| 模型与渠道统一价格 | 模型配置默认及自定义倍率，渠道应用后可覆盖，沿用已有价格版本与复制机制 | 第 4.1–4.3 节 |
| 长上下文与成本悬浮 | 实际命中阶梯才标 `1M`，费用入口在成本金额，展示规则、单价与倍率 | 第 4.4–4.5、6 节 |
| Responses 历史恢复修复 | 完整追溯历史，恢复结果独立于缓存；不能完整恢复时不发送残缺工具上下文 | 第 11 节 |
| 联合验证 | 大历史续聊后的模式、实际输入、长上下文计费、预算及失败行为一致 | 第 8、11.4 节 |

## 2. 已核验的事实与限制

### 2.1 官方 API 和第三方中转

| 对象 | 已核验事实 | 对本项目的意义 |
| --- | --- | --- |
| OpenAI 官方 API | 官方说明响应中的 `service_tier` 表示实际处理档位；Fast 被降为普通处理时返回 `default` 并按普通价收费 | 对遵循此契约的渠道，可以优先采用最终响应 |
| New API | 所检查版本默认过滤请求 `service_tier`，允许该字段或启用透传后才保留；常规 Responses JSON / SSE 转发保留原始响应中的字段 | 客户端发送 Fast 不等于 New API 真正向更上游发送 Fast；若最终返回 `default`，可信返回模式应按普通价 |
| Sub2API | 支持保留、过滤、拒绝和强制 Priority 等请求策略；请求 `fast` 规范为 `priority`，也接受 `ultrafast` | 需要同时记录客户端请求与实际出站请求，不能只记录统一后的一个值 |
| Sub2API 的 Codex 登录路径 | 源码与测试明确将 OAuth / setup-token 上游的 `default` 视为不可靠：有效 Fast 请求也可能得到该返回；内部计费保留出站请求档位 | 不能给所有中转统一写死“返回 default 必须普通计费”；提供显式渠道配置 |
| 未指定部署实例 | 本次核验的是公开代码快照与官方文档，没有对某家中转的部署版本、配置和账单发起真实调用 | “可传回字段”不等于“每个实例都会传回”，也不等于能验证中转背后的实际算力 |

Sub2API 的相关实现采用“上游声明只能降低计费档位”的策略，本项目不照搬这一排序规则：用户可自定义倍率，倍率未必按普通、Fast、Ultrafast 单调递增；本方案按所选计费依据确定档位，再查对应价格。该 Sub2API 快照的请求规范化已接受 `ultrafast`，但响应观测规范化列表尚未包含它，本项目应独立解析原始响应，而不是依赖中转的内部计费实现。

官方 API 文档不构成 Codex 私有登录端点的返回保证。第三方即使回显了请求档位，也只能视为“上游声明”，不能从响应耗时或输出速度证明真实模式。界面使用“上游返回”“计费档位”，避免未经证实的“实际已使用”。

### 2.2 实施前代码缺口（已补齐）

- `llm/transformer/openai/responses/outbound.go` 和 `outbound_stream.go` 没有把响应 `service_tier` 带入统一响应；Codex 复用此转换。
- `llm.Response` 已有 `ServiceTier`，但 `llm.Usage`、计费快照与 `ComputeUsageCost` 之间没有完整传递计费依据。
- `internal/objects/price.go` 的 `ModelPrice` 目前包含基础项目、上下文阶梯、时间段和渠道倍率，没有模式价格配置。
- `cost_calc.go` 不按处理档位选择倍率；`budget_pricing.go` 与费用注入、用量记录因此也不会区分 Fast / Ultrafast。
- 现有 `request_executions.response_body` / `response_chunks` 保存上游响应；`requests` 保存客户端可见响应。核验必须先读上游执行数据，不能把转换时丢失字段误判为上游未提供。

本地现存预览数据库只有演示样本，没有能够验证 Fast / Ultrafast 的真实请求。上述缺口来自源码核查，不是收费请求实测。

### 2.3 现有价格流程与 CCH 参考

AxonHub 的模型价格与渠道价格已共用 `ModelPrice` 和 `CompleteModelPriceEditor`。渠道“使用参考价”、选中模型后的回填、批量匹配均将模型的价格复制到渠道表单；它们不是持续联动的引用。后端价格模板只补缺少的渠道价，已有渠道价不随模型改价自动覆盖。执行开始时，有渠道价就采用渠道价，没有时采用模型标准价，再冻结本次价格快照。

已只读核对本地 CCH `0c508eaa`：

- 日志的成本金额本身是悬浮入口，旁边显示紧凑的 `fast`、`1M` 或 `fast · 1M` 标记；浮层展示基础费用、倍率与合计。
- 长上下文定价按有效输入量严格大于阈值触发。CCH 的 OpenAI 默认阈值为 272,000，另有 200,000 的上下文规则，不能统一理解为输入达到一百万。
- CCH 分别记录上下文窗口状态和实际定价命中。Axon 本次所需的 `1M` 是费用标记，应根据实际采用的定价规则生成，不能直接照搬窗口状态。
- CCH 的输入、缓存等用量需要相加才能获得触发量；Axon 的 `Usage.PromptTokens` 已包含缓存。只参考交互和明确的计价依据，不能复制其求和式造成重复计算。

本次不引入 CCH 的会话累计定价，也不修改现有 Axon 全量阶梯与时间段覆盖顺序。具体文件见第 10 节。

## 3. 档位判定规则

### 3.1 分开保存四个值

| 信息 | 含义 | 用途 |
| --- | --- | --- |
| 客户端请求 | 原始请求中的档位 | 按用户指定的缺失回退规则计费 |
| 发往上游 | 本次执行完成参数覆盖后的档位 | 诊断本项目是否改过请求；不覆盖客户端原值 |
| 上游返回 | 上游原始响应中的档位 | 在可信返回模式下决定结算档位 |
| 计费档位及依据 | 本次选定档位，以及来自上游、客户端或未启用模式计费 | 驱动费用、预算、注入结果和历史展示 |

`fast` 与 `priority` 统一映射为 Fast，但保存原始字符串供核验。`default` 为普通。请求未填或使用 `auto` 表示未明确指定加速档位，不能据此推断 Fast；缺少有效上游结果时按普通费率处理，并显示“未明确指定加速模式”。

响应的空串、`null`、`auto`、非字符串、无法识别的新值及互相冲突的有效声明均不作为实际档位证据；保存原值和原因，再按客户端请求处理。不能把这些情况伪装为“上游确认普通”。

`flex` / `scale` 不误认作 Fast，也不在已知非加速响应时回退成客户端 Ultrafast。本轮沿用它们现有的基础计价行为并注明未配置专项价格；Flex 折扣、Scale 合约价格不属于此次新增范围。

### 3.2 两种渠道级计费依据

| 配置 | 有有效上游返回时 | 无有效上游返回时 | 适用情况 |
| --- | --- | --- | --- |
| 优先上游返回（默认） | 使用最终返回档位；可以低于或高于客户端请求 | 按客户端请求 | 遵循官方返回契约的 API / 中转 |
| 按客户端请求 | 按客户端请求；仍记录上游原值 | 按客户端请求 | 经确认上游声明不可靠或合同明确按请求收费的渠道 |

不根据渠道名称包含 `newapi` / `sub2api` 自动切换规则。同一中转域名可能混合 API Key 和 Codex 登录账户，本项目通常看不到其内部账户类型；管理员应按该渠道的实际返回与收费约定选择。混合且无法区分的线路，不能承诺自动还原上游真实成本。

用户所说的“上游不支持就按客户端”在本方案中落实为：无法提供可信档位证据时按客户端计费。若可信上游明确返回普通，则按普通；若 `default` 本身不可信，则将该渠道配置为按客户端。

### 3.3 决策示例

下表均为规则示例，不是已执行的收费请求。

| 客户端请求 | 上游返回 | 渠道依据 | 计费结果与解释 |
| --- | --- | --- | --- |
| Fast | Priority | 优先上游返回 | Fast；依据上游返回 |
| Fast | default | 优先上游返回 | 普通；上游声明未按 Fast 处理 |
| Ultrafast | Priority | 优先上游返回 | Fast；按上游返回选择 Fast 价格 |
| Ultrafast | 未提供 | 优先上游返回 | Ultrafast；按客户端请求，实际模式未确认 |
| Fast | default | 按客户端请求 | Fast；按渠道规则计费，保留 default 原值 |
| 未指定 / auto | Ultrafast | 优先上游返回 | Ultrafast；上游声明决定费用，详情提示与请求不同 |
| 未指定 / auto | 未提供 | 任一依据 | 普通；没有明确的加速档位证据 |
| 任意 | 任意 | 未启用加速计费 | 沿用原有计费，不附加模式倍率 |

### 3.4 JSON、流式和重试

1. JSON 读取响应顶层 `service_tier`；Responses SSE / WebSocket 读取终止事件内的 `response.service_tier`。优先采用与终局 usage 同属一次响应的声明。
2. `response.created` / `response.in_progress` 只代表过程状态，不直接决定最终费用。终局缺少有效声明时按客户端规则处理，不拿初始占位值冒充实际结果。
3. 同步覆盖现有支持的 `response.completed`、失败 / 不完整终止事件；若接入的中转使用 `response.done` 等已核验别名，复用对应终止处理。没有用量时保留当前结算语义，不凭档位生成 Token 数。
4. Chat Completions 读取实际响应或用量块中的声明；跨多个块的有效声明冲突时视为证据不足，记录冲突并使用客户端规则。明确可用的最终声明优先。
5. 每次执行独立收集证据。切换渠道、重试、连接复用时清空上一执行的响应档位，禁止把失败渠道的 Priority 带入成功渠道结算。
6. 无论同协议透传还是经过协议转换，证据都从上游原始响应获取；对客户端返回只保留上游真实声明，不把“计费用的回退值”伪造成上游字段。

## 4. 官方默认与自定义倍率

### 4.1 配置位置和优先级

沿用“模型标准价 → 渠道应用或覆盖 → 请求价格快照”的流程，不新增一套独立的全局 Fast 价格表。

| 位置 | 可配置内容 | 保存后的作用 |
| --- | --- | --- |
| 模型页 → 模型编辑 → 定价 | 标准模式基础价、上下文阶梯、Fast / Ultrafast 官方默认或自定义 | 保存该模型的标准价格；供渠道应用，以及无渠道价时的现有模型价格回退使用 |
| 渠道 → 模型价格 → 使用参考价 / 批量匹配 | 选择参考模型，同时复制基础价、阶梯、模式倍率及来源版本 | 保存独立的渠道价格；不建立自动更新的绑定 |
| 渠道 → 某个模型 → 加速模式倍率 | 每档选择已应用的模型配置、官方默认或自定义 | 只影响该渠道该模型；其他渠道和模型标准价不变 |
| 渠道 → 计费依据 | 启用加速计费、优先上游返回 / 按客户端请求 | 决定该渠道如何识别计费模式，不放进模型标准价格 |

模式倍率与基础价、阶梯一起保存在共享 `ModelPrice` 中，模型页和渠道页复用同一个价格编辑器。官方匹配在配置时解析，不能用全渠道固定 Fast ×2 覆盖所有模型。渠道已有价格时采用其完整配置；无渠道价时采用模型标准配置。已有渠道价缺少模式配置时显示未配置，不在结算时悄悄从最新模型设置拼补，避免混用两个版本。

“模型配置”表示上次应用并保存的副本，界面注明参考模型与应用版本。“重新应用模型配置”在当前表单中只替换两档模式设置；顶部“使用参考价”和批量匹配继续替换完整价格。模型改价后，已配置渠道只有再次应用并保存才更新。渠道未配置价格而使用模型回退的，新执行仍按当时模型配置冻结；已在途执行不变。

例：模型 Fast 为 ×2，渠道 A 应用后改成 ×1.6，渠道 B 保留 ×2；模型随后改成 ×2.2，A 和 B 仍保持原值。A 再次点击“重新应用模型配置”并保存后变为 ×2.2。模型修改不会静默抹掉渠道的自定义价格。

- 官方默认：按明确的 OpenAI 官方模型标识和上下文范围匹配。已知模型可自动匹配；中转别名需要明确选择参考模型，不能模糊匹配名称。
- 自定义：允许非负十进制数，包括 0、1 和小于 1 的折扣，不限制 Fast 必须大于 1 或 Ultrafast 必须大于 Fast；负数、空值和无效数值不可保存为自定义倍率。
- Fast / Ultrafast 分别覆盖，可以一项使用已应用模型配置、一项自定义。选择来源不会立即保存，恢复官方默认也只修改当前表单。
- 官方数据无某档位时显示“官方未提供”；管理员仍可针对中转提供的服务填写自定义倍率，但界面不得标为官方支持。

### 4.2 已核对的默认价格关系

来源为 2026-10-31 读取的官方 API 价格页。表中倍率是相对该模型相同上下文档位的普通单价，不是速度倍数，也不是 ChatGPT 订阅额度的消耗倍数。

| 官方模型 | Fast | Ultrafast | 边界 |
| --- | ---: | ---: | --- |
| GPT-6 Astra | ×2 | ×6 | 分别应用于官方短 / 长上下文对应单价 |
| GPT-6.1 Sol | ×2 | ×6 | 分别应用于官方短 / 长上下文对应单价 |
| GPT-5.5 | ×2.5 | 官方未提供 | 仅对已发布 Fast 价格的上下文范围提供默认 |
| GPT-4.1 | ×1.75 | 官方未提供 | 不能按统一 ×2 处理 |
| GPT-4o | ×1.7 | 官方未提供 | 不能按统一 ×2 处理 |

官方默认按“模式单价 ÷ 普通单价”解析到输入、输出、缓存读写及上下文档位。仅当所有适用项比例相同时，界面展示一个统一倍率；比例不同则显示“按官方分项”并展开各项，不能取平均数。自定义模式倍率则统一作用于该模型现有 Token 计费项。

复用现有价格目录和版本记录，并补充经过核验的服务档位数据及来源日期；不在每次请求时联网查询官方价格。选择默认时保存解析结果和来源版本。新增官方数据后，编辑页可提示更新，需显式应用并保存才影响后续请求，不静默覆盖自定义配置或历史价格。

### 4.3 费用计算顺序

```mermaid
flowchart LR
  A[读取本次请求和上游最终返回] --> B[按渠道规则确定计费档位]
  B --> C[选取基础价格和上下文或时间段规则]
  C --> D[按输入 输出 缓存分别应用模式倍率]
  D --> E[应用现有渠道或上游分组倍率]
  E --> F[同一结果用于费用明细 预算结算和费用注入]
```

计算公式：`Token 项费用 = 用量 / 1,000,000 × 基础单价 × 模式倍率 × 本项现有成本倍率`。

保留已有全量阶梯与时间段覆盖的选择顺序；时间段配置仍表达普通模式基础价，再应用模式倍率。独立按次费用、图片固定费用不自动乘模式倍率，保持现有规则。使用 Decimal 计算，统一在现有结算边界舍入，不让前端另算一套账。

当前上游余额 / 分组倍率和手动渠道倍率由既有逻辑选择，不能将两者重新一起相乘。模式倍率是在选定的成本倍率之外独立的一层；费用明细明确展示来源，不能把合并后的倍数冒充“渠道倍率”。

示例：GPT-6.1 Sol 普通输入 $2 / 1M，输出 $10 / 1M；非缓存输入 10,000、输出 2,000，基础费用 $0.04。Ultrafast ×6、渠道 ×0.8，最终为 `$0.04 × 6 × 0.8 = $0.192000`。相同用量若可信上游返回 Fast，则为 `$0.04 × 2 × 0.8 = $0.064000`。若自定义 Ultrafast ×4.5，则为 $0.144000。

若现有基础价已经含 Fast 加价，开启模式倍率前需改回普通基准价，或显式把模式倍率设为 1，避免重复加价。

### 4.4 长上下文与 `1M` 标记

`1M` 在成本旁表示本次采用长上下文定价，不代表输入已到一百万，也不等于模型声明支持一百万上下文。单价中的 `/1M` 仅表示“每百万 Token”，与这个标记含义不同。

复用现有 `ModelPrice.VolumeTiers`：以本次请求的总输入 `PromptTokens` 选择整套价格，严格大于 `Above` 才进入对应档。输入恰好为 272,000 时仍用标准上下文价；272,001 才命中该长上下文档。缓存已包含在总输入中，不再相加；输出不参与阈值判断。命中后，非缓存输入、输出和缓存分别使用该档单价，作用于各项的全部用量，不仅是超出阈值的部分。

为区分长上下文规则和一般数量折扣，统一全量阶梯补充可选的“长上下文”用途标记。官方导入在来源明确时设置；自定义阶梯由管理员在同一编辑器中标记。该字段只说明规则用途，不再参与一轮收费。旧阶梯缺少标记时仍照常计算，浮层展示具体阶梯，不凭模型名、阈值或高价猜成 `1M`。分项的 `usage_tiered` / `usage_volume` 也不自动等同于长上下文规则。

价格选择返回最终命中的规则与价格项：基础价、长上下文全量阶梯或时间段覆盖。当前时间段会覆盖整套项目；若它覆盖了长上下文价，就显示“时间段价格”，不能仍标 `1M` 或声称收取了长上下文价。多档时记录真正生效的一档，不仅保存“输入超过阈值”。

模式计费是否启用不影响长上下文规则本身。标准模式也可能显示 `1M`；Fast / Ultrafast 使用标准上下文价时只有模式标记。长上下文价已体现在单价中，后续只应用模式倍率与现有成本倍率各一次。

以下为 GPT-6.1 Sol 的方案示例。标准上下文单价为输入 $2、输出 $10、缓存读 $0.10 /1M；长上下文阈值为 >272,000，单价分别为 $4、$15、$0.20 /1M。请求输入 300,000（含缓存读 60,000），输出 2,000：

| 费用项 | 采用的用量与单价 | 基础费用 |
| --- | --- | ---: |
| 非缓存输入 | 240,000 × $4 /1M | $0.960000 |
| 缓存读 | 60,000 × $0.20 /1M | $0.012000 |
| 输出 | 2,000 × $15 /1M | $0.030000 |
| 基础合计 | 已包含长上下文定价 | $1.002000 |

Fast ×2、渠道 ×0.8 的最终费用为 `$1.002 ×2 ×0.8 = $1.603200`，标记 `Fast · 1M`。相同用量的标准模式为 $0.801600，只标 `1M`；Ultrafast ×6 为 $4.809600，标 `Ultrafast · 1M`。不能在这些金额上再乘一次长上下文加价。

### 4.5 费用明细与证据

后端持久化本次计费模式、决议依据、模式倍率来源、最终上下文规则、触发量和阈值，以及各项原始单价、基础小计、模式调整后小计、现有成本倍率和最终金额。字段名在实现时沿用现有对象风格；可用内部 `serviceTierPricing`、`contextPricing` 表达两组独立证据，不把它们拼成多个模式枚举。

当前 `buildCostBreakdown` 通过 `总额 ÷ 倍率` 还原基础费用，无法准确表达自定义 0 倍率、分项倍率或固定费用混合。新记录直接展示后端保存的费用明细，不能倒算基础费，也不能读取当前模型价重建历史。旧记录沿用已有展示，不补造缺失的模式或上下文证据。

请求涉及多个计费用量或不同执行时，各份证据独立保存；汇总有不同模式、规则或倍率时明确显示“混合”并分项说明，不能选一个 Fast 标签代表全部。列表、详情、预算和费用注入共用已计算结果，前端只格式化和组织展示。

## 5. 预算、历史和升级行为

### 5.1 预算预估与最终结算

- 发送前尚无上游返回：使用本次冻结的价格与客户端请求档位进行预算预估，标识为预估；不伪装为最终处理模式。
- 收到用量后：按第 3 节规则重新选择计费档位，用同一价格版本计算实际费用。预留与实际的差额通过既有结算流程处理，不能把实际费用上限限制在预估值。
- 费用注入、用量日志、密钥 / 分组预算与成本汇总共享已计算的明细和总额，避免分别实现档位规则。
- 流中断后已有可结算用量时按既有规则处理；没有用量不生成虚假费用。恢复任务必须使用保存的档位证据与价格，而不是当前渠道设置。
- 缺少官方倍率不是“上游没返回档位”，不能因此再次回退成普通价。该模式费用标记未计价；普通请求和不依赖预算的转发继续。只有既有预算确实需要预估金额的请求沿用原来的准入限制；已发送但费用未知时沿用 `budgetcharge.StatusUnknown` 保留预留并待核对，不按零元结清。

后续补充倍率只影响新执行，不自动给历史未计价请求补扣。历史未计价记录保留具体原因，沿用现有未知费用处理；如需追溯重算，应另行明确价格依据和重算范围，不由定时恢复任务套用最新价格。

### 5.2 保存配置与结算结果

本次执行开始时固定：开关、依据、客户端与出站档位、模型官方映射、基础价与上下文阶梯版本、模式倍率及已有成本倍率。响应到达后追加终局观测、实际价格命中和决议，保存到用量费用记录和预算恢复证据。

`request_executions.cost_snapshot` 现为不可变字段：保留其发送时快照，不把响应后得出的结论回写到不可变字段。可在 `llm.Usage` 的内部计费元数据中携带响应观测，使现有 `budget_charges.usage` 能保存；最终用量记录保存补全后的费用快照。内部计费元数据不能未经转换直接暴露为供应商协议字段。

每条已结算记录应能回答：请求了什么、发出了什么、上游返回了什么、最终按什么档位、是否采用长上下文价格、输入如何跨过阈值、采用哪版单价和倍率。即使正文存储关闭或过期，这些标量证据仍可供费用核对。

### 5.3 存量兼容与生效时间

建议既有渠道缺省为未启用，新建渠道也需显式启用，避免升级后给已自行加价的渠道重复乘倍率。开启后使用已经应用的模型模式配置；缺少配置时可应用模型标准配置、官方参考或自定义。开关本身不静默替换已有价格。

历史记录缺少新字段时显示“历史记录，未记录模式”，按原已保存金额展示，不根据现行官方价格重算。关闭模式计费后保留配置草稿，后续请求按原基础计费，历史加速费用不变。

每次执行在准备发送时取得快照；保存只影响之后开始的执行，已在途执行保持原值。重试产生的新执行使用当时的渠道配置，明确避免跨执行复用旧返回证据。

优先通过已有 JSON 设置、价格版本、费用快照和用量字段增加可选成员，暂不为了档位筛选新增列、索引或迁移。若实施证明必须新增 schema / data migration，再依据仓库发布基线和迁移规范安排；不改已发布迁移。序列化缓存变化需核对现有结构和版本，不能仅因旧 JSON 可解析就认定兼容。

现有价格导出格式已有版本 2。若新字段超出旧格式，新增明确版本的导出格式；兼容读取已发布的旧格式，并将缺少模式设置的旧文件按未启用处理，不能无提示地忽略新设置。

### 6.4 交互与布局验收约定

- 基础价格仍是原有可编辑控件，新增倍率不替换基础价编辑，不把默认参考与当前生效值混写。

当前 [会话恢复代码](../../internal/server/orchestrator/responses_session.go) 有两个相互叠加的问题：`lookupOrLoad` 只取得一轮原始请求和响应；随后调用 `record` 并再次从缓存读取。前者将增量误当完整历史，后者把“超过缓存限制”误当“无法恢复”。`prepare` 一旦拿到这样的部分记录，就移除 `previous_response_id`，上游既没有完整历史，也失去了继续查找历史的编号。

当前工作区已有 `ErrContinuationUnavailable`、对应的 `previous_response_not_found` API 错误，以及停止自动重试的处理。这些改动属于已有工作，需复用。它们无法发现上述部分恢复：因为编号已被提前删除，传输层看不到未恢复的标志。修复必须回到历史恢复的完整性，不能只再增加一层报错转换。

### 11.2 修复契约与模块职责

推荐由现有会话恢复层统一组装历史，数据库服务继续提供每轮有权限约束的读取；每个步骤都走同一 API Key 和项目上下文。

1. **追溯到完整起点。** 缓存未命中时读取对应已完成请求；若其原始请求仍带 `previous_response_id`，继续查找更早一轮，直到无前序编号的起点或已确认完整的缓存记录。按从旧到新的顺序组合每轮 input 和 response.output，再追加当前 input，各项只追加一次。保留工具 call ID、条目顺序、既有状态字段归一化和当前会话 ID；不删除孤立工具结果来掩盖缺失。
2. **恢复结果直接返回。** 把完整记录的构造与缓存插入分开。构造成功后直接交给当前请求；满足现有容量与有效期限制时才缓存。不再用“写缓存 → 再读缓存”作为恢复成功判据，不靠提高 1 MiB 上限解决问题。未展开的增量请求不得以完整记录身份进入缓存。
3. **完整性决定是否删除编号。** 仅当整条历史已恢复，才将完整 input 写入当前请求并移除前序编号。祖先不存在、正文未保存或已清理、记录结构无法恢复时，明确返回不可恢复状态，不发送部分拼接的请求。循环引用也不能被当作完整起点；实现应使用可检查的遍历并响应上下文取消，不用任意截断后的部分历史继续转发。
4. **保留已有传输边界。** 对必须由 Axon 展开历史的 Codex / WS 桥接路径，复用 `ErrContinuationUnavailable` 和 `previous_response_not_found`，不再切换渠道重试同一个残缺请求。原本允许上游原生续接的普通 Responses HTTP 路径，继续保留完整的前序编号与原始增量交给上游；不能把本次修复变成所有路径都要求本地拥有历史。已完全展开的请求可以沿现有规则更换传输，不改变“发送后结果未知不得自动重放”的约定。
5. **区分缺失与读取故障。** 数据库或外部正文存储读取错误保留原来的错误原因，不一律伪装成“历史不存在”；日志只记录必要的响应标识和失败分类，不导出工具正文。需要补齐历史的路径在无法恢复时停止发送，普通不带前序编号的请求不受影响。

直接调整位置：

| 位置 | 责任 |
| --- | --- |
| [responses_session.go](../../internal/server/orchestrator/responses_session.go) | 追溯、顺序组合、完整性与缓存写入分离，构造结果直接返回 |
| [orchestrator.go](../../internal/server/orchestrator/orchestrator.go) | 接收恢复结果 / 错误，保留当前请求参数与会话上下文，衔接已有处理入口 |
| [RequestService 历史读取](../../internal/server/biz/request.go) | 每轮继续按 API Key、项目、已完成状态和支持格式读取；使用既有正文存储接口 |
| [传输执行器](../../llm/transformer/openai/responses/transport_executor.go)、[重试出口](../../llm/pipeline/pipeline.go)、[API 错误映射](../../internal/server/api/upstream_error_policy.go) | 复用不可恢复错误和停止重试，只补必要的直接契约衔接，不覆盖其他任务的传输改动 |

不需要数据迁移或改写已有请求。缓存未命中时会增加按历史轮数读取的成本；可在已确认完整的缓存祖先处停止追溯，避免无意义的重复读取。正文完全未保存或已删除的链无法凭空恢复，客户端需携带完整上下文重新发起。提高缓存上限、静默丢掉工具结果、重试或换渠道均不作为根因修复。

### 11.3 与模式计费、长上下文的衔接

恢复的对象是历史消息，不是历史请求的整份参数或账单。当前请求的 `model`、`service_tier`、工具定义、instructions 等参数保持本轮语义；尤其不能把上一轮 Fast 复制成这一轮的客户端模式。上一轮的返回档位、价格快照和预算记录也不能成为本轮证据。

```mermaid
flowchart LR
  A[本轮参数与增量输入] --> B[补齐完整历史输入]
  B --> C[按当前渠道发送并冻结本轮价格]
  C --> D[取得本轮上游档位和用量]
  D --> E[选定本轮模式与上下文价格]
  E --> F[结算预算并展示成本悬浮]
```

本轮费用使用上游本轮返回的 usage。恢复后的历史可能被模型再次读取，属于本轮上游报告的输入；不能只按客户端新增的几条工具结果计价。同时不能将之前各轮的 usage 再相加，否则会重复收费。长上下文阈值使用本轮实际总输入，缓存仍不重复相加。

发送前预算预估应沿用已经准备好的完整请求及本轮价格；不能因为客户端只发一个工具结果，就把预估输入当作很小的增量。恢复失败且尚未发送时，不生成上游 Token 消耗；如该路径已建立预留，沿用原有未发送失败的释放规则。发送后未知状态继续遵循已有预算未知处理，不与“本地恢复失败”混为一类。
