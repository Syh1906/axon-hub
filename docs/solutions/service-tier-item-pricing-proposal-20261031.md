# 加速模式分项计费：灵活配置方案

状态：2026-10-31，最终预览已获确认，分项配置、统一解析、预算与恢复、逐项冻结证据、模型／渠道编辑及成本浮层已实现并完成定向联调。未提交、未发布。继续复用现有价格体系，不另建计费系统。验收记录见[实施与验收](../../output/implementation/axon-item-pricing-20261031/verification.md)。

## 要解决的情况

以下是说明机制的自拟例子，不代表某款模型的官方报价：普通输入 $2 / 百万 Token、输出 $10；Fast 输入 $4、输出 $25。对应输入 ×2、输出 ×2.5，统一 ×2 会低估输出费用。缓存读取、5 分钟 / 1 小时缓存写入，以及不同上下文档位也可能有不同价格。

推荐支持三种日常用法：只填统一倍率；在统一倍率上覆盖少数项目；直接使用官方完整分项规则。界面默认保持简单，分项和上下文覆盖放在展开区。

## 配置方式与确定的覆盖顺序

每个 Fast / Ultrafast 模式分别保存一套规则：

| 层级 | 用途 | 示例 |
| --- | --- | --- |
| 模式默认 | 未单独指定项目时的倍率 | Fast 默认 ×2 |
| 模式分项 | 覆盖输入、输出、缓存读取、缓存写入变体 | 输出 ×2.5；缓存读取 ×1.5 |
| 当前基础价格档的模式覆盖 | 仅在命中某个长上下文档或时间段时使用 | 长上下文输出 ×3 |

一次计费先按现有规则确定基础价格档，再选当前模式。针对每个 Token 项，按以下顺序找第一个明确值：

1. 当前命中价格档的分项规则。
2. 当前命中价格档的统一倍率。
3. 模式通用分项规则。
4. 模式通用统一倍率。

上下文规则挂在已有价格档上，复用现有严格大于阈值的判断；不另设一份可能不一致的上下文阈值。时间段覆盖仍按现有逻辑先确定基础价，只有明确配置模式覆盖才改变上述继承结果，不能同时套用已被时间段替代的长上下文规则。

字段应能区分“继承”“明确值”“未配置价格”：空白表示继承，数值 0 表示免费；明确未配置价格会停止该项向下继承。缺少可用规则时记为未定价，不能自动当 ×1。未启用加速计费与 Standard 模式沿用现有行为。

## 倍率与独立单价

每个分项规则只能选择一种计价方式：

- **相对基础价的倍率**：`最终项目单价 = 当前基础单价 × 分项倍率`。适合中转成本按本站基础价比例变化。
- **指定模式单价**：直接填写该模式的每百万 Token 单价。适合官方分项价、供应商独立报价，以及基础价为 0 无法计算比值的情况。

两种方式互斥，不能先应用指定单价再乘模式倍率；现有渠道成本倍率仍在项目计费之后只应用一次。固定按次、图片等非 Token 项不因为增加分项能力而参与模式倍率。单独的加速图片或按次收费需另有明确需求。

这种结构既支持“倍率灵活调整”，也避免强行用除法表示所有官方报价。保存金额与倍率继续使用 Decimal，不使用浮点计算金额。

## 官方参考与自定义

官方数据保存模型标识、来源、抓取 / 核验日期、版本、币种、计费单位、适用上下文范围与各项单价。导入时按相同模型、相同项目、相同上下文范围配对；有可比的非零普通价时计算倍率。

- 所有适用项比例相同：显示“统一 ×N”，仍保留来源证据。
- 比例不同：显示“官方分项”，展开各项；不取平均数。
- 普通价为 0、缺少可比项或供应商直接报价：使用指定单价，不计算无意义比值。
- 官方没有公布某个项目或范围：明确标记未配置，不能继承另一个上下文档的官方价格来猜测。管理员可主动填写自定义值。

“按官方比例”和“使用官方模式单价”是有实际金额差异的两种选择：若本站基础价已被用户修改，前者随本站基础价缩放，后者保持官方绝对单价。界面必须明确展示选择及计算预览，不能把自定义基础价乘官方比例后仍称为官方实际金额。

官方更新先展示变化，由管理员应用；不会悄悄覆盖已保存配置或历史账单。渠道应用模型规则后保存独立副本；后续编辑渠道不影响模型，模型更新不自动改写已应用渠道。

## 一次请求怎样计算

沿用当前服务模式判定：有效上游终局优先、无效或缺失按客户端，或渠道明确固定客户端依据。解析模式与选定价格是两件事，不因需要分项价格改变上游证据。

以最初自拟例子为例，非缓存输入 100,000、输出 10,000，Fast 输入 ×2、输出 ×2.5，渠道成本倍率 ×0.8：

| 项目 | 普通单价 / 百万 Token | 分项倍率 | 模式单价 | 项目金额 |
| --- | ---: | ---: | ---: | ---: |
| 输入 | $2 | ×2 | $4 | $0.40 |
| 输出 | $10 | ×2.5 | $25 | $0.25 |

合计为 `(0.40 + 0.25) ×0.8 = $0.52`。若错用统一 ×2，则得到 $0.48，少算 $0.04。

预算预估、响应费用、持久化用量、重启后结算使用同一个价格解析函数。每项冻结基础价格档、规则来源、计价方式、倍率或指定单价、最终单价、用量和小计，以及现有成本倍率。之后修改模型、渠道或官方目录，不重算历史请求。

## 界面与可核验性

模型和渠道价格编辑器沿用现有位置，默认显示统一倍率。展开“分项设置”后编辑输入 / 输出 / 缓存及变体；上下文档内显示自己的可选覆盖。提供明确的“继承”“自定义倍率”“指定单价”“未配置”状态与生效值预览，避免靠空白猜含义。

成本金额旁继续使用橙色 Fast / Ultrafast 与紫色 `1M`，不新增一串分项标记。浮层逐项显示实际倍率或指定单价；所有项目相同才显示一个统一倍率，否则显示“按分项计价”。保留旧记录无证据的提示。

增加一组可编辑示例用量预览，用于比较改前 / 改后金额。这是配置预览，不声称能预言供应商实际使用量或最终扣款。

## 迁移与验收边界

当前已存统一倍率可作为新结构的默认倍率，旧 JSON 缺少覆盖字段时继续使用该倍率；历史快照不改写。实施前核对当前字段是否已正式发布，再决定是否需要新版本结构或数据迁移，不能为了本地未发布草稿引入冗余兼容逻辑。

必要验收覆盖：输入 / 输出倍率不同；缓存读写变体；阈值前 / 等于 / 后；时间段覆盖；0 与继承；明确未配置；基础价 0 + 指定模式单价；渠道复制后独立修改；配置改动不影响旧账单；预算预估、结算与恢复一致；JSON/SSE/WS 同一证据；前端保存回读与分项浮层。

主要代价是规则解析、冻结明细和表单复杂度增加。用一个默认倍率加少量覆盖控制复杂度，不添加表达式语言、任意条件脚本或通用规则引擎。先实现上述明确计费维度，避免扩大为整个定价系统重构。
