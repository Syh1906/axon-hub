# Cost Tracking

AxonHub provides real-time cost calculation and usage tracking for every request.

## Overview

Cost tracking in AxonHub helps you monitor and control your AI spending across all providers and models. Each request is automatically analyzed and cost is calculated based on configurable pricing.

### Usage statistics and consumption leaderboard

Project **Usage statistics** summarizes requests, tokens and costs by user or API key. The admin **Consumption leaderboard** adds user/key/channel cost and cache rankings with expandable model details. Both pages support Today, Yesterday, This week, This month, All time and Custom dates in the system timezone; weeks start on Monday.

Project statistics retain owner access. The system-wide leaderboard requires the system-level `read_leaderboard` permission and has no separate management permission. Cache-hit rate only includes requests with cache reads or writes. Cache coefficients normally lag by 15–20 minutes; missing historical samples display an em dash. See [statistics semantics](../development/consumption-statistics.md) for fields, formulas, deleted-entity behavior and upgrades.

## Features

### Token Type Tracking

AxonHub tracks the following token types:

| Token Type | Description | Code |
|------------|-------------|------|
| **Input (Prompt)** | Usage records include cached input; the billing item uses non-cached input after subtracting cached portions | `prompt_tokens` |
| **Output (Completion)** | Tokens generated by the model | `completion_tokens` |
| **Cache Read** | Tokens read from cache | `prompt_cached_tokens` |
| **Cache Write** | Tokens written to cache | `prompt_write_cached_tokens` |
| **Reasoning** | Reasoning tokens (for supported models) | `completion_reasoning_tokens` |
| **Cache Write (5 min)** | Anthropic 5-minute TTL cache write | `prompt_write_cached_tokens_5m` |
| **Cache Write (1 hour)** | Anthropic 1-hour TTL cache write | `prompt_write_cached_tokens_1h` |

### Pricing Modes

AxonHub supports the following pricing modes:

| Mode | Description | Use Case |
|------|-------------|----------|
| **Flat Fee** (`flat_fee`) | Fixed fee per request | Fixed cost scenarios |
| **Image specification fee** (`image_fixed`) | Match each final image to a tier or dimension rule, then sum fees | Resolution-based image pricing |
| **Usage Per Unit** (`usage_per_unit`) | Price per 1M tokens | Most models |
| **Tiered** (`usage_tiered`) | Tiered pricing based on usage | Volume discount scenarios |

### Image specification fees

Select **Image specification fee** in the existing price row in a channel's model prices or a model's pricing editor. Automatic identification is on by default: enter per-image prices for 1K, 2K and 4K. Zero is valid; empty prices cannot be saved. Time overrides share the editor. Channel rules apply only to that channel and model. Importing a standard price copies its complete rules for independent editing.

Automatic tiers prefer explicit response labels, followed by labels in the actual outgoing request, accepting both `2K` and `2k`. Request labels are marked as unconfirmed upstream and do not prove the provider's final charge. Without labels, AxonHub reads final PNG/JPEG/WebP dimensions, then response dimensions or `widthxheight`. Known Gemini dimensions match first; other sizes use pixel-area bands up to `1024²`, `2048²` and `4096²`. These are local billing bands, not a longest-edge rule: `2048×512` belongs to 1K by area. Larger or unknown sizes remain unpriced.

Turn automatic identification off to define conditions. **Width or height exceeds** and **Exact dimensions** fill common rules; adjust dimensions, numbers and comparisons (`>`, `≥`, `=`, `≤`, `<`) and select **Match any** or **Match all**. Drag handles reorder rules. Each image uses only the first match. Automatic tiers and manual rules retain their own prices, conditions and order across switches and saved edits. Unfinished drafts in the inactive mode do not affect billing. Manual rules use output dimensions, not requested dimensions.

Example rules, in order: either dimension above 2048 costs 0.08; either dimension above 1024 costs 0.04; exactly 1024×1024 costs 0.02. One 1024×1024 image and one 2048×2048 image total `0.02+0.04=0.06` before the channel's manual multiplier. These are sample rates, not provider quotes. Billing uses the frozen request price version; upstream token-group multipliers do not apply to image fees.

Supported evidence includes OpenAI Images-compatible responses with per-image sizes, Gemini image parts, completed Responses image-generation results and Chat Completions `image_url` content. Streams are billed after final aggregation, excluding partial previews and Gemini thought images. An asynchronous task ID alone is not a completed image. Unrecognized formats still return normally and remain unpriced. URL inspection reads a bounded image header from public HTTP(S) destinations without channel credentials or private-network access; failed reads may still use response dimensions or explicit labels.

Image charges are logged even when provider token usage is absent, without fabricating token usage. Breakdown entries retain image dimensions, matched rules and evidence sources. If any image cannot be priced, the total is unpriced while known image entries remain available; this is not a zero-cost record.

## Configuration

### Fixed per-key cost multipliers

Choose manual or upstream mode in [channel balance and rate settings](channel-management.md#upstream-balances-and-per-key-rates). If local token prices produce a base cost of $1, key A at 0.5× costs $0.50 and key B at 0.8× costs $0.80. A retry selecting B captures B's rate for that attempt; no average is used.

Each attempt records a masked key label, price version, pricing time, multiplier and source. Response `usage.cost` and persisted usage share that snapshot. Synchronization, manual edits or channel disabling during a stream do not reprice it. Historical records and backups retain the captured result. An upstream rate alone cannot produce a cost without a local model price.

The upstream multiplier is applied once, rather than multiplied by the manual value again. Independent flat charges retain the manual multiplier. Valid previous values after temporary failures are marked cached. Rates older than 30 minutes, beyond a known upstream time boundary or without verified identity use the manual fallback and are marked estimated. `UsageLog.costSnapshot` exposes the token multiplier and source. `costPriceMultiplier` returns the multiplier shared by the billed items, or null for mixed multipliers; the breakdown labels these as mixed without deriving one base total. Older records still use their historical price version.

Local base prices must match the upstream base pricing and exclude group multipliers. These are local cost estimates, not a guarantee of the final upstream invoice.

### Model Pricing

Configure pricing for each channel and model in the admin dashboard:

1. Go to **Channels** → **Model Prices**
2. Set pricing items for each model:

![Model Pricing](../../screenshots/axonhub-model-price.png)

   - Input price (`prompt_tokens`)
   - Output price (`completion_tokens`)
   - Cache read price (`prompt_cached_tokens`)
   - Cache write price (`prompt_write_cached_tokens`)

#### Cache Write Variants (Anthropic)

For Anthropic models, you can configure TTL variants for cache writes:
- **5 minutes** (`five_min`): Short-term cache
- **1 hour** (`one_hour`): Long-term cache

The model catalog provides only the 5-minute cache write price. When you import a price by selecting a model from the catalog's official Anthropic source, a `one_hour` cache write variant is added automatically at twice the input price (Anthropic's 1-hour cache write multiplier); other sources do not get it. Without a `one_hour` variant, 1-hour writes are billed at the base cache write price.

With [Force 1-Hour Prompt Cache](channel-management.md#force-1-hour-prompt-cache) enabled on a channel, cache writes mostly land in the 1-hour tier, so make sure the price includes a `one_hour` variant.

### Cost Calculation Logic

1. **Input Token Calculation**: `PromptTokens - CachedTokens - WriteCachedTokens`
   - Cached tokens are billed separately at different rates

2. **Cache Write Variant Processing**:
   - If `WriteCached5MinTokens` or `WriteCached1HourTokens` are present, use corresponding variant pricing
   - Otherwise, use the default cache write price

3. **Price Versioning**:
   - Each price change creates a new version record
   - Usage logs reference the specific price version via `cost_price_reference_id`

### API Response (`usage.cost`)

Whether a cost appears on the client response is controlled by the **Inject usage.cost** setting in system settings, which is off by default. When the setting is on and the channel has a price configured for the model, AxonHub calculates the request cost from the channel model price and writes it to `usage.cost` on the client response.

A few notes:

- The number is AxonHub's own calculation from the channel model price, not the upstream provider's bill.
- `usage.cost` or `cost_details` returned by the upstream is dropped and never forwarded to the client (except on pass-through requests).
- With the setting off, clients do not see `cost` on the normal request path.
- `cost` is omitted when no price is configured, the response has no `usage`, or the setting is off.

#### Pass-through and binary endpoints

Pass-through requests return the upstream body as-is, including any `cost` the upstream included. AxonHub does not calculate or modify it. Binary endpoints such as `POST /v1/audio/speech` return audio data with no JSON `usage`, so no cost is returned either.

#### Supported response fields

- OpenAI Chat Completions / Completions / Responses / Compact: `usage.cost`
- OpenAI Embeddings / Image Generation / Video: `usage.cost`
- Anthropic Messages: `usage.cost` (in `message_delta` when streaming)
- Gemini `generateContent`: `usageMetadata.cost` (AxonHub extension; official Gemini responses do not include this field)
- Jina Embeddings / Rerank: `usage.cost`
- AI SDK text: `usage.cost`

```json
{
  "usage": {
    "prompt_tokens": 100,
    "completion_tokens": 50,
    "total_tokens": 150,
    "cost": 0.000005
  }
}
```

#### Streaming responses

Where `usage.cost` appears in a streaming response depends on the protocol:

- OpenAI Chat Completions / Completions: `cost` is on the chunk that carries `usage`, typically the last chunk before `[DONE]`; the client must send `stream_options.include_usage`.
- OpenAI Responses: `usage.cost` is on the `response.completed` event.
- Anthropic Messages: `usage.cost` is in the `usage` of `message_delta`, and the stream ends with `message_stop`.
- Gemini `generateContent`: `usageMetadata.cost` is in `usageMetadata`, and the stream ends with `candidates[].finishReason`.
- AI SDK text: `usage.cost` is in the `usage` of the `e: finish` event.

## Viewing Costs

### Usage Logs

Each request's usage log contains:

- **Token Usage**: prompt_tokens, completion_tokens, total_tokens
- **Token Details**: Breakdown of various token types
- **Cost Information**: total_cost, cost_items, cost_price_reference_id

### GraphQL API

Query usage logs with cost information:

```graphql
query GetUsageLogs {
  usageLogs {
    edges {
      node {
        modelId
        promptTokens
        completionTokens
        totalTokens
        totalCost
        costItems {
          itemCode
          quantity
          subtotal
          tierBreakdown {
            upTo
            units
            subtotal
          }
        }
        costPriceReferenceId
      }
    }
  }
}
```

### Cost Fields Description

| Field | Type | Description |
|-------|------|-------------|
| `totalCost` | Float | Total cost calculated based on channel model price |
| `costItems` | JSON | Array of cost breakdown items |
| `costPriceReferenceId` | String | Reference ID to the price version used for cost calculation |

## Best Practices

1. **Configure Model Prices**: Set accurate prices for each channel and model before use
2. **Monitor Cache Usage**: Cache can significantly reduce costs; monitor cache hit rates
3. **Use Price Versioning**: Price changes automatically create versions for cost traceability
4. **Review Regularly**: Check usage logs and cost reports to optimize usage

## Troubleshooting

### Missing Cost Data

If costs are not showing:

1. Verify channel model prices are configured
2. Check if the provider returns token usage
3. Review the `costPriceReferenceId` in usage logs

### Incorrect Costs

If costs seem incorrect:

1. Verify pricing configuration (especially cache prices)
2. Check token count details in usage logs
3. Confirm the correct price version was used
4. For tiered pricing, verify tier configuration is correct
