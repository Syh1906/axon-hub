# API Key self usage

Administrators can edit a group's name or note using the pencil in Project → Key groups, and enable or disable it with the inline switch. Click a quota to set, increase, or remove that period's limit while retaining usage and reset schedules. Click expiry to extend it, choose a date, or remove expiry, then save; renewal does not enable a disabled group. Batch management retains its preview workflow. Cycle settings and quota resets remain available under Advanced in the row menu.

If the submission result was received but the list failed to refresh, use Refresh in the editor without saving again. If the request outcome is unknown, defer recovery and resume the original operation from the page; already successful operations are not repeated.

Select **View usage with an API Key** on the admin sign-in page, or open `/self-usage` directly. Enter a **user** or **personal** API Key; no admin account is needed. Other key types cannot use this page.

The page shows the key name and the system time zone. You can switch languages and themes. The key is stored only in this browser tab's session storage: a refresh in the same tab keeps you signed in, while closing the tab or selecting **Log out** ends the page session. Logging out does not revoke the API Key; revoke it in the admin area if needed.

The default range is the last 7 days. Choose today, yesterday, the last 7 days, the last 30 days, this month, or a custom range of at most 90 days (both dates included). Dates and request times follow the displayed system time zone; each daily total uses the request creation date. The summary lists successful and failed requests, tokens, and cost, with a per-model breakdown. The request log supports model and status filters and pagination. Processing requests may appear in the log but do not count as successful or failed. Tokens and costs from failed or canceled requests count if usage records were saved. A request with multiple usage records counts only once toward request totals.

Summary, model totals and token chart axes use K/M/B; hover or keyboard focus exposes exact counts. Model rows show cache reads divided by input tokens, or “—” when input is zero. Statistical costs follow the system's decimal-place preference. Request logs retain the admin request page's precision: six decimal places for request and breakdown amounts, and two to six for unit prices, regardless of the system preference.

The request log reuses the admin request page's presentation: ID, raw status and HTTP code, streaming mode, channel name (when the group permits it), model routing and executed-model tooltip, reasoning budget/effort, protocol and cache markers, tokens, combined read/write cache and hit rate, cost, duration, caller, and creation time. Cache tooltips include 5m/1h writes. Duration shows first-token latency, total duration, and the server-calculated output speed; unavailable metrics show “—”. Caller group and key names occupy separate lines. Hover over or focus a cost to see the saved input, output, cache read, cache write (including 5m/1h variants), and other cost items, their effective per-million-token unit prices, tiers, and the base total, multiplier, and total. The base total and multiplier are always shown; at "×1" the base total equals the total. Items from multiple usage records are combined; when the records' multipliers differ, the multiplier shows "Mixed" and the base total shows "-".

Costs use the system currency. In the summary, daily trend, and per-model table, no usage records means zero cost; entirely unpriced usage shows “—”. Partially unpriced usage shows the known cost with an unpriced-record count, while a genuine zero price displays zero. The request log matches the admin request list: a request without usage records shows “-” in the token, cache, and cost columns, and entirely unpriced usage shows a “-” cost without a breakdown.

By default this page shows **API-originated requests for this key in its project**. Grouped keys can switch to group usage for totals, trends, models and logs across current members in the same project. Caller labels include the key and group names. After reassignment, subsequent statistics queries update the group label as well. Changing only the log status, model or page also refreshes both totals and logs when a membership change is detected, preserving the log filters. Switching scopes does not reuse the old group cache. The server derives group membership from the authenticated key; callers cannot choose arbitrary group IDs. Ungrouped keys have no group toggle. Both scopes exclude Playground and test requests. The log omits request and response bodies, upstream key hints and remarks, and error details. Channel information follows the current group setting. If sign-in or queries happen too frequently, the page asks you to try again later; restricted keys may also be denied access.

The group list's Usage link opens `/self-usage` in a new tab with that group selected. This entry uses the signed-in administrator and explicit project permissions, never a member credential, so empty groups and disabled keys' history remain available. The former group usage route redirects to the shared standalone page.

The **Page width** menu offers Standard (up to 1280px), Wide (default, up to 1600px), and Full width for the whole usage content area. This browser preference survives reloads and key changes. Switching width does not query data again or reset dates, filters, or pagination. Narrow windows scroll horizontally inside the table; truncated channel names expose their full text on hover.

Model-name checks compare each execution's channel model, upstream-reported model, and execution status, together with the request status. Missing fields in the self-service projection no longer turn otherwise verifiable requests into unknown results. Processing, failed, and genuinely missing historical records retain their distinct messages. These checks do not depend on channel-name visibility.

## Managing key groups

Project administrators manage recipients from **Key groups** in the project sidebar. The API keys page remains the complete key view. Groups are not login accounts and do not change member permission types or routing. Group names are unique within a project, and keys may remain ungrouped. Only project administrators may change membership because it grants group usage visibility. Deleting a group ungroups its members; destination name conflicts reject that row without deleting keys or requests.

The key list supports multiple group filters and default groups, including an explicit Ungrouped option. Defaults are stored in this browser per user and project, applied immediately on save and on subsequent visits. Deleted saved groups remain visible as unavailable choices and can be explicitly removed and saved; filtering is never silently widened. Temporary filters do not overwrite defaults; cancel discards edits; clearing defaults removes filtering. Group options use query caching and refresh after mutations. Membership changes also refresh related key, request and statistics queries.

Statistics use **current membership**: moving a key from A to B moves its retained historical usage to B; ungrouping excludes it from group statistics. This stores only one group reference per key and needs neither per-request snapshots nor history rewrites. Historical membership at request time cannot be reconstructed. Ungrouped keys are excluded from group summaries and rankings while retaining individual usage.

Key labels in requests, selectors and statistics use “key name · group name”, or “key name · user name” when ungrouped. Backup 1.6 includes group objects when keys are selected, preserving empty groups, notes, enabled state, and channel-name visibility. Restore resolves project/group names and follows the key skip/overwrite/error strategy. Older formats remain readable; formats without group state retain their original default-enabled behavior, and a missing channel-visibility field defaults to off. Older applications reject 1.6 rather than silently dropping suspension state.

### Key names and groups

Key names are unique within a project and group. Ungrouped keys form a separate naming scope. Different groups, including the ungrouped scope, may reuse a name. Moves and group deletions that would create a duplicate in the destination are rejected without changing membership; rename the key or choose another destination first. Disabled and archived keys retain their names. Management OpenAPI name selectors accept `groupRef` (0 for ungrouped). An ambiguous name requires an explicit group or a key ID.

### Group management and bulk distribution

Rows show notes, visible member counts, expiry and five shared budget periods (available / limit). Search group names, notes or key names, filter status and change sort order. Expanded members have independent pagination. Ungrouped is an organizing view without a shared budget or group enable/delete actions. Current-project `read_api_keys` grants reads of personal keys in that project. Writes still require `write_api_keys`; project isolation remains enforced.

Suspending a group blocks member requests without changing each key's own enabled state. Re-enabling it leaves individually disabled keys disabled. Group and individual restrictions both apply. Moving a key does not move charges already posted to the previous group's budget ledger; usage reports continue to aggregate current membership.

- **Single creation:** create initial keys with a group, or add a key with its current group fixed. Templates, individual budgets, expiry and IP restrictions are optional. Personal is the default type; service accounts require explicit scopes. Results remain visible until you choose to continue, which retains group/configuration and clears the name.
- **Bulk groups:** paste names or Excel columns, or import CSV after mapping columns. Shared settings include budgets and an initial key set. Override, duplicate, remove or restore inheritance per row. Shared-default edits preserve custom rows.
- **Bulk keys:** generate the same names across selected groups, or specify a group, name and template per row. Regeneration only appends missing pairs. Submit up to 100 rows at a time, with at most 100 initial keys per new group.
- **Bulk management:** choose groups or keys; changing the mode clears selection. Select-all applies to the current page, cross-page selection uses IDs, and changing projects clears it. Groups support notes, status, shared budgets/expiry and deletion. Keys support templates, individual budgets/expiry, IP restrictions, moving, status and archiving. Only checked fields change; clearing notes, limits or expiry is explicit.

Preflight conflicts and settings before submitting selected valid rows. Invalid rows remain editable. Multi-column imports use one mapping for the whole table: a missing or blank group cell is rejected, and Ungrouped must be explicit. Single-column key lists inherit a target only when exactly one is selected, including an explicit Ungrouped selection. For multiple targets, generate combinations or provide a group column per row. Each new group, its initial keys, templates and budgets commit or roll back together. Results are tracked per row. Unknown outcomes recover the original batch instead of generating new credentials. You can dismiss recovery temporarily and reopen it from the page. Another batch cannot overwrite the unresolved request. With browser storage unavailable, the request remains in memory for the current page; with session storage available, it also survives refreshing the same tab. Recovery does not undo previously successful rows.

Keys remain masked until an operator explicitly copies or exports selected results. Copying API and self-usage URLs is also explicit. Concurrent edits require closing and refreshing before review. Budget edits preserve settled and reserved usage; resetting usage remains a separate budget action.

Individual group members support inline name, expiry, five-period budget and enable/disable edits. Settings uses a direct-save form. Single creation submits without manual preview; validation failures preserve the draft. Usage summaries include an overall cache-hit card beside cost, with per-model read/input tokens on hover or keyboard focus.

### Channel names on the usage page

When creating a group, **Show channels on usage page** is directly available after the note and defaults to off. Bulk creation supports shared defaults and per-row overrides. For existing groups, select this field in edit or bulk management before setting the switch; an omitted field remains unchanged. Changes take effect on the next request-log query without signing in again.

When enabled, current-key usage, group usage, and the administrator's group usage entry show read-only channel information in the admin request page order: request ID, channel, model. Names prefer the saved execution snapshot and follow the same adopted-result, retry, and parallel-execution selection rules as the admin page. The cell includes the request multiplier, new/reused/returned session state, and channel tags. Hover or keyboard focus shows the full name, provider, session state, tags, and request multiplier. Session states use the full history within the project and session, independent of the visible date range or page; unfinished requests retain an unknown state. Multipliers follow billed usage when available and preserve mixed, zero, and missing-snapshot states. Upstream key hints, remarks, and routing diagnostics are not exposed. Hidden or ungrouped requests receive none of these channel fields from the server. Reassignment applies the current group's policy to retained history. The original admin request page keeps its own permissions.
