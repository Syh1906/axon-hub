# API Key self usage

Select **View usage with an API Key** on the admin sign-in page, or open `/self-usage` directly. Enter a **user** or **personal** API Key; no admin account is needed. Other key types cannot use this page.

The page shows the key name and the system time zone. You can switch languages and themes. The key is stored only in this browser tab's session storage: a refresh in the same tab keeps you signed in, while closing the tab or selecting **Log out** ends the page session. Logging out does not revoke the API Key; revoke it in the admin area if needed.

Choose today, yesterday, the last 7 days, the last 30 days, this month, or a custom range of at most 90 days (both dates included). Dates and request times follow the displayed system time zone; each daily total uses the request creation date. The summary lists successful and failed requests, tokens, and cost, with a per-model breakdown. The request log supports model and status filters and pagination. Processing requests may appear in the log but do not count as successful or failed. Tokens and costs from failed or canceled requests count if usage records were saved. A request with multiple usage records counts only once toward request totals.

The request log includes a caller column and shows ID (raw status and streaming badge), model, tokens (total, input, output, reasoning), cache reads (quantity and hit rate), cache writes (quantity and write rate), cost, duration, and creation time in the labeled system time zone. Duration appears only for completed requests: streaming requests show first-token and total duration, and non-streaming requests show total duration. Hover over or focus a cost to see the saved input, output, cache read, cache write (including 5m/1h variants), and other cost items, their effective per-million-token unit prices, tiers, and the base total, multiplier, and total. The base total and multiplier are always shown; at "×1" the base total equals the total. Items from multiple usage records are combined; when the records' multipliers differ, the multiplier shows "Mixed" and the base total shows "-".

Costs use the system currency. In the summary, daily trend, and per-model table, no usage records means zero cost; entirely unpriced usage shows “—”. Partially unpriced usage shows the known cost with an unpriced-record count, while a genuine zero price displays zero. The request log matches the admin request list: a request without usage records shows “-” in the token, cache, and cost columns, and entirely unpriced usage shows a “-” cost without a breakdown.

By default this page shows **API-originated requests for this key in its project**. Grouped keys can switch to group usage for totals, trends, models and logs across current members in the same project. Caller labels include the key and group names. After reassignment, subsequent statistics queries update the group label as well. Changing only the log status, model or page also refreshes both totals and logs when a membership change is detected, preserving the log filters. Switching scopes does not reuse the old group cache. The server derives group membership from the authenticated key; callers cannot choose arbitrary group IDs. Ungrouped keys have no group toggle. Both scopes exclude Playground and test requests. The log omits request and response bodies, channels, upstream models, and error details. If sign-in or queries happen too frequently, the page asks you to try again later; restricted keys may also be denied access.

## Managing key groups

Project administrators manage recipients from **Key groups** in the project sidebar. The API keys page remains the complete key view. Groups are not login accounts and do not change member permission types or routing. Group names are unique within a project, and keys may remain ungrouped. Only project administrators may change membership because it grants group usage visibility. Deleting a group ungroups its members; destination name conflicts reject that row without deleting keys or requests.

The key list supports multiple group filters and default groups, including an explicit Ungrouped option. Defaults are stored in this browser per user and project, applied immediately on save and on subsequent visits. Deleted saved groups remain visible as unavailable choices and can be explicitly removed and saved; filtering is never silently widened. Temporary filters do not overwrite defaults; cancel discards edits; clearing defaults removes filtering. Group options use query caching and refresh after mutations. Membership changes also refresh related key, request and statistics queries.

Statistics use **current membership**: moving a key from A to B moves its retained historical usage to B; ungrouping excludes it from group statistics. This stores only one group reference per key and needs neither per-request snapshots nor history rewrites. Historical membership at request time cannot be reconstructed. Ungrouped keys are excluded from group summaries and rankings while retaining individual usage.

Key labels in requests, selectors and statistics use “key name · group name”, or “key name · user name” when ungrouped. Backup 1.6 includes group objects when keys are selected, preserving empty groups, notes and enabled state. Restore resolves project/group names and follows the key skip/overwrite/error strategy. Older formats remain readable; formats without group state retain their original default-enabled behavior. Older applications reject 1.6 rather than silently dropping suspension state.

### Key names and groups

Key names are unique within a project and group. Ungrouped keys form a separate naming scope. Different groups, including the ungrouped scope, may reuse a name. Moves and group deletions that would create a duplicate in the destination are rejected without changing membership; rename the key or choose another destination first. Disabled and archived keys retain their names. Management OpenAPI name selectors accept `groupRef` (0 for ungrouped). An ambiguous name requires an explicit group or a key ID.

### Group management and bulk distribution

Rows show notes, visible member counts, expiry and five shared budget periods (available / limit). Search group names, notes or key names, filter status and change sort order. Expanded members have independent pagination. Ungrouped is an organizing view without a shared budget or group enable/delete actions. Existing personal-key visibility is preserved.

Suspending a group blocks member requests without changing each key's own enabled state. Re-enabling it leaves individually disabled keys disabled. Group and individual restrictions both apply. Moving a key does not move charges already posted to the previous group's budget ledger; usage reports continue to aggregate current membership.

- **Single creation:** create initial keys with a group, or add a key with its current group fixed. Templates, individual budgets, expiry and IP restrictions are optional. Personal is the default type; service accounts require explicit scopes. Results remain visible until you choose to continue, which retains group/configuration and clears the name.
- **Bulk groups:** paste names or Excel columns, or import CSV after mapping columns. Shared settings include budgets and an initial key set. Override, duplicate, remove or restore inheritance per row. Shared-default edits preserve custom rows.
- **Bulk keys:** generate the same names across selected groups, or specify a group, name and template per row. Regeneration only appends missing pairs. Submit up to 100 rows at a time, with at most 100 initial keys per new group.
- **Bulk management:** choose groups or keys; changing the mode clears selection. Select-all applies to the current page, cross-page selection uses IDs, and changing projects clears it. Groups support notes, status, shared budgets/expiry and deletion. Keys support templates, individual budgets/expiry, IP restrictions, moving, status and archiving. Only checked fields change; clearing notes, limits or expiry is explicit.

Preflight conflicts and settings before submitting selected valid rows. Invalid rows remain editable. Multi-column imports use one mapping for the whole table: a missing or blank group cell is rejected, and Ungrouped must be explicit. Single-column key lists inherit a target only when exactly one is selected, including an explicit Ungrouped selection. For multiple targets, generate combinations or provide a group column per row. Each new group, its initial keys, templates and budgets commit or roll back together. Results are tracked per row. Unknown outcomes recover the original batch instead of generating new credentials. You can dismiss recovery temporarily and reopen it from the page. Another batch cannot overwrite the unresolved request. With browser storage unavailable, the request remains in memory for the current page; with session storage available, it also survives refreshing the same tab. Recovery does not undo previously successful rows.

Keys remain masked until an operator explicitly copies or exports selected results. Copying API and self-usage URLs is also explicit. Concurrent edits require closing and refreshing before review. Budget edits preserve settled and reserved usage; resetting usage remains a separate budget action.
